## 2. Deep independent research: what a real resource management environment needs

### A. Resource truth, observability and safe optimization
From Microsoft official APIs/documentation: physical installed/visible/available memory, commit charge/limit, Working Set vs Private Bytes, mapped shared model pages, file cache, memory pressure, page faults/hard faults, peak allocations, process tree, Windows memory compression, pagefile, kernel/user consumption, CPU load/power/thermal throttling, GPU UMA reserved/shared driver allocations. Explain limitations of simple Task Manager sums and what real system-level counters a future dashboard must show. Separate observation from enforcement, allocation caps from real physical reservation and reclamation from mere working-set trimming. Evaluate official Windows performance and resource counters, PDH/ETW/PerformanceCounter/CIM, GlobalMemoryStatusEx, memory resource notifications, and practical low-frequency sampling options. State actual operator overhead as publisher-measured vs UNKNOWN; do not invent 20/100/500MB figures or 'RAM boosters'. Never recommend disabling compression/pagefile, purging standby memory or editing BIOS as default optimization.

### B. Native Windows CONTAINMENT / PROCESS GOVERNOR
Compare Windows Job Objects (owned child tree, JOB memory commit, CPU-rate/priority, nested jobs, kill-on-close/notifications), process launch/assignment races and access rights, scheduling/affinity/EcoQoS/priority, Task Scheduler session/user accounts, service lifecycle, Windows user-session app vs administrator service; and ready products: [lowleveldesign Process Governor](https://github.com/lowleveldesign/process-governor) official, [Process Lasso license](https://bitsum.com/apps/process-lasso/docs/deployment/licensing/) and current Free edition, genuine current identity/version of different ProcGovernor names, WinSW/NSSM/services only if they fit, Process Explorer/System Informer for observation, other *new* independently discovered Windows managers. Distinguish OS kernel ENFORCEMENT, CLI wrapper, all-system service/beta elevated service and monitoring/dashboard; a job commit cap can produce OOM and cannot guarantee a physical RAM quota for mapped model data. Consider fail-closed launch only for owned processes, not manipulating unrelated browser or entire Windows processes.

Precisely test via documentary evidence whether an EXISTING FREE Windows product can be safely controlled through public CLI/API and supply required governance so that a custom low-level supervisor is unnecessary. Score support for named jobs, child propagation, cancel/restart/timeout, process ownership, least privilege, per-session control, developer API, idle RAM, maintenance, commercial terms, stability.

### C. One shared engine and model resource lifecycle (future integration, not choosing weights yet)
Compare engine/model lifecycle managers with documented load/unload/idle/keepalive/limits and their own process cost: llama.cpp server/router including v0.7.0 tagged docs and newer findings; Ollama; LM Studio llmster; Jan Desktop model API; Lemonade; KoboldCpp; llama-swap or better heterogeneous proxy, and new credible Windows-native engines if they solve a missing issue. Do NOT make a second model manager mandatory when the chosen server already owns lifecycle. **One heavy inference lease by default**; keep models unloaded until needed if physically advantageous, stream/queue rather than parallel resident 4 models. Compare model file mapping, KV cache/context slots, server-vs-GUI footprint, auto-evict TTL, router child processes, sleep/worker process leftovers, unload state verification, concurrency controls and cancellation, client overrides to keep_alive. A single endpoint can spawn multiple model workers; prove actual behavior from published docs, never infer that one URL=one OS process. No GGUF/model download, benchmark, or suggested default context/model without measured fit. Evaluate how the future controller would lease an engine and keep one running model shared among logical assistants.

### D. Resource admission & scheduling policy — distinguish from AI agents
Investigate complete architecture of **monitor → admit/deny/queue → bounded worker allocation → unload/pause → release/reconcile** with explicit user foreground OS/browser reserve, live available RAM + commit headroom + hard faults, CPU fairness, non-starvation, OOM/fail closure, unknown-peak tasks, model load bursts, cancellation, user override and optional lower-priority background work. Resource governor has to handle *non-AI specialist programs* as well (document conversions, OCR, browser, media). No arbitrary fixed safe RAM MB thresholds without measured task. Distinguish "pause a process" from "free its committed memory", and "sleep the engine" from "free complete tree"; no automatic killing unrelated processes.
Compare deterministic finite queue and Task Scheduler, ready workflow engines **Dagu** / minimal durable queue / .NET Channels, Go channels, Python async, DBOS/SQLite, exactly which capabilities are missing from ready tools. Distinguish GUI monitoring from workflow system, durable ledger vs model conversation memory, and safe restart from automatic re-send of an ambiguous external action. Seek minimal viable scope without a resident agent framework, heavyweight web stack, Linux VM, browser or database server.
