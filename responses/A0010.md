## 1. Executive technical conclusion

**خلاصهٔ تصمیم‌پذیر:** برای شروع، ساخت یک «سیستم‌عامل چنددستیار» یا اجرای چند مدل هم‌زمان ضرورت ندارد. کوچک‌ترین گزینهٔ معتبر، یک محیط آمادهٔ همیار یا گردش‌کار قطعی، یک سرویس استنتاج مشترکِ قابل تخلیه و ابزارهای محدودِ درخواستی است. اگر صف سراسری، کنترل واقعی منابع و بازیابی کارها بعد از قطع برنامه لازم باشد، یک کنترل‌کنندهٔ کوچک Windows-native توجیه پیدا می‌کند. برای این نقش، .NET و Go رقیب‌های اصلی‌اند؛ Python برای ابزارهای AI و اسناد بسیار مناسب است، ولی نصب فعلی آن دلیل برتری معماری نیست. کیفیت فارسی، مصرف کل RAM و سرعت مدل‌های کوچک روی این دستگاه هنوز تعیین نشده و هیچ گزینه‌ای مجوز ساخت نگرفته است.

**Engineering answer (ANALYSIS):** first buy/use/configure the capabilities that already exist; write only the missing policy. Ready apps already supply conversations, model selection, tools, project workspaces and sometimes schedules, approvals and delegation. Inference servers already supply streaming, model APIs and model lifecycle. Windows already supplies process grouping, scheduling and pressure signals. What is not supplied as a verified complete contract by any researched ready product is DJMRN's combination of system-wide admission control, separate source authorities, narrowly approved external actions, durable unknown-result reconciliation and usable behavior in this particular 5.88GiB-visible environment.

This yields three independently reviewable choices, which may share processes:

1. **Human-supervised first assistant:** compare goose Desktop + one shared server, a ready LM Studio/Bionic local route, and Jan Desktop. No custom always-running host is justified merely to label two assistant roles.
2. **Persistent controlled jobs:** compare a small .NET user-session controller, a Go controller, and Dagu around deterministic workers. Build the permission/outbox/resource boundary only where product configuration cannot express it.
3. **More complex reasoning workflows:** add LangGraph or Microsoft Agent Framework only when explicit branching/checkpoint/delegation requirements justify their dependencies. Pydantic AI is a serious alternative for typed tools; its current V2 persistence capabilities must not be described using old V1 limitations.

**Most consequential verified deltas:**

- llama.cpp has a versioned stable release **v0.7.0, October15**, and its tagged server documentation includes model routing, explicit load/unload, a resident-model count control and idle sleep that releases model/KV memory. An extra llama-swap process is therefore optional, not a compulsory ingredient.
- LM Studio **0.4.26** is separate from its headless **llmster** daemon and from **Bionic**, a separate agent app. Bionic has a documented local Free plan; its cloud plan is paid and is not a free hybrid solution.
- Jan Desktop **0.8.7** is a current stable comparison candidate. Current Cowork and standalone Agent documentation still identifies preview/nightly delivery. Agent CLI approval and shell sandbox are separate, and default plain CLI execution auto-approves tools.
- Microsoft Agent Framework .NET/Python have a production 1.x line; the current Python release is **1.22.0**. The Go SDK **0.1.1 is explicitly prerelease**, not equivalent maturity. AutoGen now explicitly disclaims fixes/support and warns about archival use; it is not a greenfield production finalist.
- DBOS current configuration docs support SQLite, including Python's default SQLite route and an optional pure-Go driver. Older PostgreSQL-only README text conflicts with current reference documentation and cannot be used to require a PostgreSQL server.
- Fresh Hugging Face pricing and the original documentation source both now say **Free users have no included Inference Providers monthly credits**. The older $0.10/month assertion in accepted history is not current entitlement.
- No remote provider passed all of renewable-free, specific Iranian-user eligibility, privacy, commercial use and no-overage gates in this round. The remote-assisted bundle is a complete **conditional alternative**, with remote inference disabled, not a secretly approved fallback.

Official evidence appears beside each comparison and in §14. Documentation establishes a feature exists; publisher performance and security claims are not independent validation. Exact Windows idle RSS/peak, interactive latency and Persian task quality remain **UNKNOWN** unless explicitly identified as historical observations.

### 3.2 Standalone comparative reviews

**C#/.NET versus Go for the controller (A).** If the first-class requirement is Windows-native process supervision plus an accessible tray/settings window, C# is the strongest practical starting hypothesis: direct Windows ecosystem, typed async code, existing UI options and service/event integration. Use a small console/worker backend if UI is unnecessary; do not pull WPF/WinUI into a headless controller. Native AOT is a separate packaging candidate, not an obligation, and WPF should not be promised as universally AOT-compatible. A normal self-contained .NET worker is a credible easier-maintained comparator.

Go can win when the desired artifact is a portable daemon with a tiny local HTTP status page and very few dependencies. Its advantage is packaging and straightforward concurrency, not guaranteed lower whole-stack RAM. Windows API wrappers, handle cleanup, service integration and ACLs must be engineered; a Windows-native control plane is not automatically more correct because it is compiled. Compare equal policy contracts, not an empty Go webserver against a Python agent with many loaded libraries.

**Rust (A).** Valuable when native isolation/handle safety, embedding an engine, or long-lived resource primitives dominate and the maintainer can own the complexity. The current Duroxide preview offers an interesting durable-Rust path. That does not justify Rust for ordinary routing and a few process launches. Compiler/toolchain footprint is principally a development cost; prebuilt workers do not require installing a compiler on the user's laptop. No measured advantage over .NET/Go here overcomes engineering cost automatically.

**Python versus JS/TS (A).** Python is favored for task workers requiring document, numerical, ML and linguistic packages; use independent pinned environments, loaded only for that task. Python3.15 being newest does not make every native wheel available. JS/TS is favored when most work is existing MCP/client/web integrations or an agent SDK such as Pi; its event-loop model suits network queues but CPU-bound transforms need subprocesses/workers. In both, a small native supervisor helper can own Job Objects instead of forcing all code into one language. A helper adds a process/build boundary and should be omitted if a reviewed library provides equivalent controls.

**PowerShell and no custom host (A).** PowerShell is appropriate for a narrow approved Windows action with validated arguments and fixed scope. It is a poor universal privilege-bearing tool callable by an arbitrary model prompt. If the user only wants supervised research/document drafting, a ready app can remove custom controller, framework, service and database entirely. That is a real architecture option.

### 3.3 Lifecycle, single instance and maintenance

Proposed requirements, not configuration performed:

| Concern | Smallest adequate pattern | Escalate only when |
|---|---|---|
| Startup | User launches app; later start-on-login or user Task Scheduler task | Background work before login is explicitly needed; then a restricted service plus separate user UI |
| Single instance | Per-user named mutex/OS lock and one queue owner; validate identity beyond a PID | Separate users or machines need their own instances |
| Worker boundary | Typed subprocess input/output, explicit executable and permitted files; no shell string interpolation | Shared long-lived worker demonstrably saves measured startup cost |
| Pinning | Exact app/engine release, model hash/template, lockfile, worker environment; keep prior verified package | A required fix/model cannot run with current pin |
| Update | Deliberate separate review; backup/checkpoint, compatible schema and suspended new admissions | Never auto-migrate solely because an updater exists |
| Rollback | Restore package AND compatible state snapshot; keep source projections reconstructible | DB/workflow history format changed: old binary alone may not read it |
| Observability | Rotated structured local events, per-job correlation and selected counters | Add external telemetry/dashboard only with explicit need/data permission |
| UI | CLI/status page or small tray; keep renderer closed when idle if product supports it | User actually needs a dashboard; do not require Electron and a browser simultaneously |

Source facts for current toolchain versions do not establish a deployment choice. There is no recurring license fee for a locally built open-source controller, but maintenance, backups, signing and electricity remain real costs.

**Jan versus ready alternatives — standalone assessment (A).** Jan is strong when user wants local GUI/model management without another interpreter stack. Its API's configured key can be absent, CORS is enabled by default, verbose request/response logging is on by default and “execute tools on server” is disabled by default according to [API documentation](https://docs.jan.ai/desktop/api-server). The chosen tool executor must be explicit: tools returned to a client differ from tools executed by the server. Connecting two clients to the same engine reuses the server only if both actually point to that instance; starting another app's bundled engine does not.

LM Studio is stronger for documented headless/lifecycle/SDK control; llmster removes the GUI dependency. Bionic is a separate ready-task option, not proof that LM Studio's developer server supplies all Bionic semantics. goose gives a mature general tool-agent interface with CLI/API escape paths, but Rust core does not erase its Electron desktop footprint. AnythingLLM is favored for a user who genuinely wants document ingestion/RAG and ready flows; otherwise its embedding, conversion and knowledge-store machinery is avoidable. Open WebUI becomes more compelling for shared authenticated users, not automatically for a single laptop. AionUi's team UI can remove custom delegation UI, but “many CLI backends supported” is not a reason to run all of them.

**Critical security distinction (D/P):** [Jan Agent overview](https://docs.jan.ai/agent) says plain CLI auto-approves; safe mode prompts for writes/shell/MCP but does not enable shell sandbox; sandbox is another option, off by default in CLI, described as always on for desktop chat agent. Approval rules/thread grants can bypass prompts. This is not evidence that every child, external MCP server or Windows tool is confined. Current0.8.7 release notes include Windows command-approval and cancellation fixes; past successful narrow read tests do not certify all future actions. No command is proposed or run here.

### 5.2 Standalone lifecycle review: eliminate duplicate managers first

**llama-server now versus adding llama-swap (D/A).** The [v0.7.0 tagged server README](https://github.com/ggml-org/llama.cpp/blob/v0.7.0/tools/server/README.md) was obtained through GitHub after web retrieval failed, blob4e4472ec24bd0822be30e327aecd549cc15a2bc8. It explicitly supports:

- router-mode model management, POST /models/load and /models/unload, model SSE status and model presets;
- resident model count setting with documented default4; unlimited is possible, therefore low-RAM safety is not automatic;
- idle sleep disabled by default; when enabled it unloads model and KV memory, and reloads on a new task;
- /health, /props, /models and /metrics do not wake the sleeping model;
- context/parallel slot/KV type/cache-RAM controls. Some current defaults are sized for much larger systems.

Thus a direct single-server route may remove an entire proxy. Router mode can add child processes: “one shared service endpoint” does not always mean one OS process. v0.7.0 also changed native default port to9931; old8080 examples are not a version-independent contract. This report supplies no setup commands.

[llama-swap v265](https://github.com/mostlygeek/llama-swap/releases/tag/v265) remains a useful MIT Windows Go manager when different executables/engines must be swapped, custom profiles are useful or its UI/API is preferred. The [current README](https://github.com/mostlygeek/llama-swap) documents TTL, model-specific/all unload, API keys and basic one-model swapping; advanced concurrency matrices can defeat a single-heavy-model intent. Its optional Help/MCP features add a permission surface. It is not inference, a kernel RAM limiter, or proof of external-action durability. Do not stack it over another lifecycle manager without an explicit ownership decision.

**Ollama (D/A).** The [official FAQ source](https://github.com/ollama/ollama/blob/main/docs/faq.mdx), blob9e42f77d03419a493f29d6f27e58a16f1e16c248, documents keep_alive zero for unload, negative indefinite residency, default5-minute retention, preloading, bounded queue and model/parallel controls. Parallel contexts increase memory. A client can request a keep-alive that overrides server defaults; this is why a shared host needs policy at the request boundary. Its native running-model API exposes placement/state. Registry/model convenience can justify the manager; independent copies of Ollama plus Jan/LM Studio do not deduplicate the same weights automatically.

**LM Studio (D/A).** [Headless](https://lmstudio.ai/docs/developer/core/headless), [TTL/eviction](https://lmstudio.ai/docs/developer/core/ttl-and-auto-evict), [load API](https://lmstudio.ai/docs/developer/rest/load) and [authentication](https://lmstudio.ai/docs/developer/core/authentication) supply distinct facts: llmster independent daemon; JIT; default60-minute JIT idle TTL; auto-evict previously JIT-loaded models. Explicitly loaded instances, client choices and concurrent requests require separate control. Native load/unload APIs are better lifecycle interfaces than pretending OpenAI compatibility standardizes model eviction. Closing chat GUI is not reliable proof a model unloaded.

**Lemonade (D/A).** The old server_spec file is now a pointer. Current [API index](https://github.com/lemonade-sdk/lemonade/blob/main/docs/api/README.md) and [Lemonade management API](https://github.com/lemonade-sdk/lemonade/blob/main/docs/api/lemonade.md) document /v1/load, /v1/unload, model options and /v1/health alongside compatibility surfaces. It can replace custom modality/backend management if those modalities are genuinely needed. Its catalog and automatic backend setup should not download/activate unapproved assets. Cloud offload is experimental and remains off under unknown eligibility.

**Jan (D/A).** The documented desktop API can start with a default model and reuse a loaded instance. This is useful human UX. Uniform explicit idle unloading and stable GUI-free management equivalent to the above were not established here. Do not implement resource policy by brittle UI automation when a supported lifecycle API is a requirement; choose a different engine for that role if needed. Jan remains a valid GUI comparator despite being installed; it gains no scoring benefit.

**No measured complete-stack RAM number is available.** Neither “model533MB” nor “host10MB” is permission to budget the rest away. Peak loading, prompt processing, browser navigation, document parsing and model switching often differ from idle state. Shared file-backed pages also make sums of process working sets overcount common resident pages; use system available memory plus process private/commit/working-set views, not one number.

For a conventional dense decoder, an approximate KV planning relationship is:

KV bytes ≈ layers × context tokens × KV heads × head dimension × 2(K,V) × bytes per element × simultaneous contexts.

This is an **ANALYTICAL sizing relationship, not a measured budget**. Padding, cache layout, shared/unified slots and backend workspaces change actual allocation. Hybrid/recurrent Qwen3.5/Granite/LFM state does not reduce to this formula for every layer. Long input/prefill and draft/speculative models can add material peaks. There is no assumed safe context size, process cap, CPU percentage or OS reserve in this report.

### 6.3 What kernel enforcement really promises

**D:** Microsoft distinguishes ProcessMemoryLimit/JobMemoryLimit from working-set bounds. [Working Set](https://learn.microsoft.com/en-us/windows/win32/procthread/process-working-set) is currently resident pages; trimming makes pages eligible to leave residency and may cause later faults. [Memory-resource notifications](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-creatememoryresourcenotification) signal system physical pressure, not a per-app guaranteed allowance. [AssignProcessToJobObject](https://learn.microsoft.com/en-us/windows/win32/api/jobapi2/nf-jobapi2-assignprocesstojobobject) has access/nesting restrictions and distinguishes creation-time versus late assignment.

**A:** A trustworthy future launcher should create the owned child suspended, associate it with the intended Job, verify limits/ownership then release it, to reduce a spawn-before-assignment race. Keep native handles under controlled lifetime, use kill-on-job-close where intended and ensure child handles cannot accidentally keep a supposedly closed Job alive. Do not claim this captures WMI-created processes, escaped/breakaway jobs, an already-running user browser or workers launched by an unrelated privileged service. If assignment/limit application fails, deny the job or report a restricted degraded state; do not silently launch unrestricted or elevate.

Commit-cap exhaustion can make allocation fail or a process terminate; it is containment, not graceful model eviction. A memory-mapped read-only weight file can consume resident memory without equivalent private commit. GPU driver allocations and all other apps remain outside a worker's private limit. Consequently a Job commit cap alone cannot reserve the user's physical RAM or certify a Vulkan workload safe.

CPU affinity chooses where work runs; priority changes relative scheduling; CPU-rate caps bound cycles; thread counts affect engine contention. They are not interchangeable percentages. Lower I/O or memory page priority can protect foreground work but can slow future inference. Never apply real-time/high priority or machine-wide service changes as a default “AI optimization.” No forced working-set cleaner, standby purge, memory compression disablement, locked weights or BIOS tweak is recommended.

### 6.4 Conceptual governor policy — not installed or numerically calibrated

The following **application policy proposal** fills gaps that ready tools do not universally supply:

1. **Admission:** one owner arbitrates model and heavy-tool demand using current available physical RAM, total commit headroom, observed CPU/latency and user foreground activity. Keep an explicit OS/user reserve determined only after narrow authorized measurement. Unknown model/task peak means conservative queuing, not optimistic admission.
2. **One heavy lease:** model loads/prefill/generation and memory-heavy parser/ASR/render tasks request a single mutually exclusive heavy-resource lease by default. Lightweight deterministic work may coexist only under a separately bounded worker pool. Many logical roles do not imply resident models or parallel agent loops.
3. **Lazy lifecycle:** spawn a needed worker; reuse a healthy existing model instance and exact model/configuration ID; drain active work before switching. Evict previous idle model before loading a different one. A proxy/daemon may remain idle without its model.
4. **Context discipline:** cap admitted input/output/context/parallelism/cache independently of the model's trained maximum. Retrieve only relevant snippets and a bounded tool schema set. Dynamic tool discovery saves prompt tokens, not necessarily MCP process RAM.
5. **Pressure response:** when another app needs memory, stop new admissions, cancel safe queued work or checkpoint at a safe boundary, unload idle models and reduce background concurrency. Never suspend arbitrary threads mid external effect or database transaction just to appear responsive.
6. **Pause/resume:** distinguish user pause, resource wait, approval wait, unavailable provider, retryable deterministic failure and reconciliation wait. A suspended process still holds memory; semantic checkpoint+worker exit is different.
7. **Cleanup:** detect process-tree exit/OOM, record last confirmed state, invalidate stale lease owner using job identity/handle and generation (PID alone can be reused), clean owned children, and restart with bounded attempts/backoff. Never force-close the user's unrelated browser/app.
8. **Fairness/cancel:** bounded per-role queues, priority for interactive user work and cancellation propagated through controller, model request and tool worker. Cancellation acknowledgment does not prove a remote write never occurred.
9. **Visibility:** show why a job waits, loaded model, approximate available/commit state, owner, pending effects and last successful checkpoint. Quiet foreground behavior is a feature; a hidden uncontrolled admin shell is not.
10. **No speculative cloud rescue:** RAM pressure cannot authorize network egress, new provider, paid plan, fallback model or bypassed approval. Local queue/HOLD is valid behavior.

This is not an enforceable configuration yet. The reserve, pressure hysteresis, maximum worker concurrency, idle timeout and CPU policy must be chosen against the same workload, not invented from an8GB label.

### 8.2 Protocol/transport decision table

| Interface | What it standardizes | Small local default versus escalation |
|---|---|---|
| Direct function call/typed queue | In-process data and owner-controlled dispatch | Smallest for logical roles; no broker or protocol server necessary |
| Framed JSON/JSON-RPC over subprocess stdio | Cross-language request/response, structured error/correlation | Good bounded worker contract; launch/EOF/cancel/exit and file permissions remain host responsibility |
| [MCP 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports) stdio | Tool/resource interoperability over client-launched subprocess; current per-request metadata model | Reuse existing tool adapters; multiple clients may otherwise spawn duplicate servers |
| [MCP 2026 Streamable HTTP](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http) | JSON-RPC POST with JSON or request-scoped SSE response; origin/auth/version semantics | Shared tool server only if several clients actually benefit; loopback/auth by default. Old SSE/session-resume behavior cannot be assumed |
| [A2A1.0/current specification](https://a2a-protocol.org/latest/specification/) | Agent discovery/capabilities, tasks/artifacts and cross-runtime collaboration | Useful across independently managed agents/machines; unnecessary for two functions in one controller |
| Local HTTP/gRPC | API contract, framing/status/streaming | HTTP easiest ecosystem fit; gRPC useful typed streaming but adds schema/tooling; neither creates approval/idempotency |
| Windows named pipes | Local interprocess channel with Windows ACLs | Strong Windows-only choice for supervisor/UI; client identity/ACL and remote pipe access must be explicit |
| Files/JSONL/manifest | Simple auditable batch exchange | Need atomic replace/locking/schema/hash and claim/ack ownership; raw shared folder is not a safe multiwriter queue |
| Event bus/broker | Fan-out/decoupled consumers/backpressure depending implementation | In-process events sufficient initially; no Redis/RabbitMQ/NATS required solely because “multi-agent” appears in goal |

**Current MCP correction (D/A):**2026 revision differs materially from2025. It uses request metadata rather than assuming old initialize/session semantics, and does not preserve the old resumable stream contract. The official backward-compatibility rules matter. Advertising “MCP” or supporting old SSE is not proof an installed SDK speaks2026-07-28. Select one tested client/server protocol version or documented downgrade; do not treat an interrupted stream as reliable external tool completion or a permission to repeat it.

For HTTP MCP, origin validation, localhost binding and authentication are explicit specification protections against DNS rebinding/access abuse. CORS is not authentication. A key at an inference endpoint does not grant tools permission. A2A is not a replacement for MCP, and neither is a Windows process scheduler.

### 8.4 Reliable job and effect contract

Conceptual proposed contract, reusing rather than renaming historical WORK states:

- Job: READY, RUNNING, WAITING, PAUSED, SUCCEEDED, FAILED, CANCELED. WAITING reasons include RESOURCE, APPROVAL, AUTH and RECONCILE. Each job has one owner/lease generation, source version, bounded input, role, allowed tools, budgets, deadline and evidence IDs.
- Step: deterministic transform, model proposal, read tool or external write are distinct. Tool discovery advertises capability/schema; it cannot expand grants itself.
- Approval: bound to exact target/origin, normalized content hash, recipient/operation, maximum spend/scope and expiry. Changed payload, origin or permission invalidates approval. A file-write approval does not authorize shell/browser/email.
- External operation: stable operation ID and provider idempotency key where supported; original request and intent persist before send, confirmed receipt/evidence after.
- If send times out or process dies after possible acceptance: external operation becomes **UNKNOWN_EXTERNAL_RESULT**; job WAITING/RECONCILE. On restart query original authoritative site/receipt where allowed, or ask human to inspect. Do not automatically retransmit a customer reply, payment or canonical edit.
- Replaying a completed checkpoint can return stored result; retrying an incomplete non-idempotent effect can duplicate it. A framework “exactly-once” claim applies only inside its specified transactional boundary, never arbitrary website actions.
- Cancellation stops new tool dispatch and attempts safe current cancellation, but does not retract a committed external action. Audit records that uncertainty.

For multiple logical assistants, persist role-specific contexts and tool grants and exchange typed task/result/evidence references. Do not copy private account/customer content into a common research memory. Shared inference weights are safe to reuse conceptually; shared unbounded conversation context is not an authority mechanism.

[SQLiteFTS5](https://sqlite.org/fts5.html) supplies text matching/ranking/tokenizers. It does not make default tokenization linguistically correct for Persian. The actual SQLite linked into Python, a Go driver, a checkpointer or an app can differ from the installed CLI; pin/audit the linked library, not just sqlite.exe. Backup must cover live consistency and retainedWAL correctly; copying a live DB file arbitrarily is not a verified backup.

[DuckDB current concurrency](https://duckdb.org/docs/current/connect/concurrency) supports its documented in-process read/write patterns; general multi-process writes are not automatically provided by an embedded file. Use for read-heavy analytics with explicit memory/spill limits later, not a default authorityDB just because it is fast.

### 9.3 Security/continuity contract for Windows and optional LAN

**Local first:** ordinary user identity; explicit executable/tool allowlist; permitted paths under a dedicated workspace; no inherited broad cloud secrets; no admin shells or shell fallback to bypass failed limits. Windows ACLs protect against other users, not every malicious process running as the same user. A tool prompt is application policy; a Job Object is resource/lifecycle control; a real OS sandbox/restricted identity constrains authority. These are three separate protections.

**Secrets:** use Windows user-bound secret facilities, e.g.[DPAPI](https://learn.microsoft.com/en-us/windows/win32/api/dpapi/nf-dpapi-cryptprotectdata), or Credential Manager with appropriate ACLs. DPAPI protects data at rest under its user/machine context; it does not prevent an agent running as the same authorized user from invoking decryption. Keep secrets out of prompts, JSONL logs, model caches, mirrored documents and process command lines. A plaintext secrets YAML in a separate file is still plaintext.

**Endpoints:** bind inference/tool/status services to loopback. Require separate API credentials where supported; restrict browser origins/Host; retainCSRF/DNS-rebinding protection. “Signed local endpoint” must mean authenticated request/identity or protected IPC, not a claim localhost traffic is magically signed/encrypted. Use short-lived grants/content hashes for privileged actions. Authentication protects access, not permission for each tool.

**LAN, only if later requested:** choose one intentionally exposed authenticated gateway or bounded server address, firewall allow only intended peers/network profile, TLS or trusted encrypted tunnel as appropriate, separate per-client identity/grants and bounded queues; leave raw inference/tool workers loopback. Do not expose unauthenticated0.0.0.0, port-forward arbitrary modelRPC, or share browser debugging ports. Remote clients share the laptop's one-heavy lease and shutdown limitations. Multiple OS users may need service/UI separation and a different security design.

**Browser/shell/document risks:** browser automation has separate website permission and logged-in session scope. A webpage/document/email is untrusted input, never an instruction to change grants or contact a recipient. CLI plugins/skills/extensions and document parsers are executable supply-chain inputs. Fixed allowed targets, schema validation and original-source provenance matter even with a small model. No website/customer account or private data accessed in this research.

**Continuity:** persist intent/checkpoint before safe shutdown, record lease owner and pending effects, resume using current grants and source freshness. Sleep/off means no local work. Optional remote timers can enqueue an event for later local handling; actually executing work while the laptop is off needs separately authorized and legally eligible powered remote infrastructure. A free scheduler/API entry does not prove a free secure always-on worker.

## 11. Reproducible decision scoring and scenario ranks

### 11.1 Method and limitations

This scores **proposed architecture suitability**, not measured implementation quality or independent security assurance. Scale1–5:1=poor fit/major obstacle,3=plausible but material gaps,5=strong documented fit. Unmeasured runtime quality remains U; lighter architecture receives a reasoned, uncertain resource score, never a fabricated measured MB result.

Weights total100: hardware/responsiveness25, native Windows compatibility15, maintenance/stability10, local/free/region10, security-policy expressibility15, interoperability10, reliable durability5, necessary simplicity5, implementation+installation+rollback cost5. ### 11.4 Evolution and omission map

Decision sequence for a later discussion, not an execution plan:
