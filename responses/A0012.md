## 3. Separate the guarantees before comparing products

“Fail-closed” is meaningful only with an explicit boundary:

| Gate | Required meaning | Why another gate does not substitute |
|---|---|---|
| **A — admission** | No heavy useful work starts unless fresh host readings, known workload envelope and global lease permit it | A CPU cap can still let a too-large task start |
| **B — required limits** | Failure to configure/assign required native limits prevents target execution | WARN-and-continue is not sufficient |
| **C — ownership** | Descendants remain in the owned scope; cleanup handles normal end and specified owner failures | Killing the root or inspecting PPIDs later is weaker |
| **D — management availability** | If operator cancel/status/receipt is required, failure to establish it prevents useful work | Native limit setup can succeed while IPC/registry fails |
| **E — recovery** | After crash/reboot, capacity and outcomes are reconciled before new dispatch | A completed root or successful wrapper exit is not a complete receipt |
| **F — foreground safety** | Real whole-system physical/commit/paging and user usability stay within an agreed envelope | None of A–E physically reserves RAM for an unrelated browser |

Strict A+B+C+D+E+F is not provided by a feature named “memory limit”. Gate C can further mean ordinary contained-tree cleanup or the stronger **no inert suspended orphan even if the parent dies between kernel process creation and Job assignment**. ProcessKit's source differentiates that edge case; the report does too.

Unknown workload peak means **QUEUE/HOLD**. No arbitrary fixed MB reserve, guessed context or model size is introduced. A one-heavy-job rule is conservative scheduling, not proof that the one job fits.

### 4.2 Preconditions, handlers, expressions and external wrappers

**Preconditions can refuse a workflow, but they do not transform Dagu's resource guard.** A ready command/expression may check a condition. If custom PowerShell/C#/other logic is needed to read host counters and enforce leases, it is new policy code even when embedded inside a “no-code” workflow.

There are four independent gaps:

1. A sample now is not a reservation for the later start. Two queues can both pass a memory test before either allocates. Serializing one queue helps only if all heavy entrants use it and no independent engine bypass exists.
2. A precondition cannot predict a future AssignProcessToJobObject rejection. A prior harmless host check is not proof for the next target's exact ancestry/rights.
3. The successful creation of a resource guard is not a documented pre-launch public receipt of successful assignment for each future child. Reading logs/metrics after launch is too late for Gate B.
4. After-failure handlers cannot undo useful work that already executed. A skip/failed run is not automatically a durable waiting item that resumes once RAM returns.

The source also includes retry paths capable of bypassing step preconditions; strict policy must cover every start/retry route rather than assuming the editor's first-run check is universal. This is a review requirement, not an assertion that every retry bypasses every root condition.

**Can procgov close the target race without a Dagu patch?** For an approved command that launches the *payload only through procgov's normal pre-associated path*, procgov can apply that payload's own limits before its code executes. This is a real improvement over Dagu's post-start resource attachment. The Dagu runner, optional shell and procgov wrapper can still start outside the inner scope, and Dagu's own required limits may have failed. If the requirement is “payload has these verified inner limits”, the wrapper can satisfy a subset; if it is “all required Dagu scopes were applied or nothing useful runs”, it does not.

The same reasoning applies to a ProcessKit CLI payload wrapper, with different lifecycle strengths/gaps below. No patch is inherently needed for invoking a ready command. Strict admission, ownership and cross-component recovery are **unproven integration**, not obtained by spelling a wrapper in a workflow.

### 4.3 Queue, API, rights and useful free scope

Dagu can retain durable queue/run history, visible status/logs, operator stop/retry and workflow structure. Reuse it if those features are needed. [Global queue docs](https://docs.dagu.sh/server-admin/queues) describe concurrency within a named queue; multiple named queues are not automatically one global capacity pool.

CLI start/enqueue/stop/retry and REST control are operational interfaces. Their successful invocation means an operation was accepted/executed at that layer, not that a required Job was assigned before target execution. No documented stock REST operation was found that attests to this future per-child condition.

[Community/Team/Pro comparison](https://docs.dagu.sh/overview/self-host-license): core workflow/UI/workers are Community; API keys are limited to two; SSO, user management and audit-log features are not assumed free. Hosted Console monitoring and paid activation are optional, unnecessary for this local foundation. Run history is not identical to paid security audit logs.

An ordinary-user on-demand server is an alternative to a WinSW-installed service. No Windows service, account, privilege or firewall rule is needed merely to compare the products. Dagu's breadth can be omitted; agent/MCP/browser/cloud features are not necessary for manager-only evaluation.


## 5. lowleveldesign procgov: exact ready boundary and corrected observability

Official latest release remains **4.1.26190, 2026-07-08T22:10:03Z**, non-prerelease metadata. Release assets include procgov.exe/zip and debug symbols; service mode is separately documented **beta**. MIT. Tag tree **642bd0263f613675133ffb465d730a2cedbd0509**.

### 5.1 Normal launch versus other paths

[Win32ProcessModule.cs](https://github.com/lowleveldesign/process-governor/blob/4.1.26190/procgov-lib/Win32ProcessModule.cs), blob **86e2e39873f72351b64df86e41bd16480d90f889**, proves the normal path uses PROC_THREAD_ATTRIBUTE_JOB_LIST at creation, CREATE_SUSPENDED, applies remaining settings and then resumes. [Win32JobModule.cs](https://github.com/lowleveldesign/process-governor/blob/4.1.26190/procgov-lib/Win32JobModule.cs), blob **6cc8bdcfd3da013d2908767c78c4ad862567a02b**, applies Job memory/CPU limits before target launch.

This is stronger pre-association than Dagu's post-start assignment and ProcessKit's create-suspended-then-assign sequence. But the strengths do not combine into an imaginary universal guarantee:

| Path / event | Actual behavior / limitation |
|---|---|
| Normal owned launch | Job pre-associated before target execution; settings errors propagate rather than intentional unbounded fallback |
| Attach to existing PID | Target has already run; access/nesting can fail; no retrospective claim |
| Run-with-token path | Creates suspended with token, then assigns; do not transfer normal JOB_LIST atomicity to it |
| Recursive disabled | SILENT_BREAKAWAY_OK is set in reviewed settings path; descendants are not automatically in the intended inner scope |
| Recursive enabled | Normal descendants should inherit scope subject to Windows documented indirect-launch/breakaway rules |
| Unhandled exception | Main prints ERROR to stderr and returns **0xff**; this is a coarse wrapper failure, not a structured unique reason |
| Post-create settings/resume error | Reviewed method closes thread handle in finally but lacks an explicit kill-on-error branch there. Combined with absent kill-on-close, a suspended leftover is a **source-level risk**, not an experimentally demonstrated occurrence |
| Required limit cannot be set before launch | Exception prevents ordinary target execution; this is not the same as Dagu warning-and-continue |
| Arbitrary wrapper crash/force kill | No KILL_ON_JOB_CLOSE found in the reviewed settings/normal CLI path; surviving Job processes are possible |
| Ctrl-C with terminate-job-on-exit mode | Explicit cancellation path calls TerminateJobObject; without that mode it can leave work running |
| nowait | Wrapper does not wait for completion; incompatible with terminate-job-on-exit / wall-time combination in parser |
| Timeout | Monitor/clock logic and explicit termination require a live owner; a wall timeout is not a kernel guarantee after owner crash |
| Root exit | Source polls Job ActiveProcesses while waiting; completion does not rely solely on root exit or a guaranteed notification |

Microsoft references: [UpdateProcThreadAttribute](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-updateprocthreadattribute), [AssignProcessToJobObject](https://learn.microsoft.com/en-us/windows/win32/api/jobapi2/nf-jobapi2-assignprocesstojobobject), [Nested Jobs](https://learn.microsoft.com/en-us/windows/win32/procthread/nested-jobs). Normal same-user child rights are a realistic path, not a promise to control elevated/protected unrelated processes.

### 5.2 Named jobs and monitor: a gap closed, and a gap retained

[Program_Monitor.cs](https://github.com/lowleveldesign/process-governor/blob/4.1.26190/procgov/Program_Monitor.cs), blob **ba2f96bc5fb0f5cfd0545c55ef154bd5facf21f1**, was inspected beyond A0011:

- It **does set an explicit pipe ACL** for the current user, SYSTEM and Administrators. A0011's question whether an ACL was merely assumed is now partly resolved. It is not an owner-only/no-admin trust boundary, nor a full security audit.
- The monitor opens/retains named Job handles and associates notification processing. Named mode adds a session monitor; killing the CLI is not equivalent to closing the last Job handle.
- Client notification channel is bounded at 20 with **DropOldest**, warning on dropped items. IPC events cannot be treated as a lossless durable resource/task ledger.
- Finally closes retained handles; without kill-on-close, closing handles alone does not terminate every live process.
- [IPC messages](https://github.com/lowleveldesign/process-governor/blob/4.1.26190/procgov-lib/IpcMessages.cs) expose MonitorJob, GetJobId, SubscribeToNotifications and responses/events. The inspected message union is not a complete public task-submission/cancel/lease API.
- Empty Job monitoring and timeout metadata do not imply adaptive host RAM admission.

Library source is reusable C#, but a published stable general SDK/package/API guarantee was not established. Release debug symbols are not a reusable DLL contract. For another ready scheduler, the documented CLI is the clearer integration surface.

[Program_CmdApp.cs](https://github.com/lowleveldesign/process-governor/blob/4.1.26190/procgov/Program_CmdApp.cs), blob **5f6f838ccf0320a729ee6eb372b0d255a7a14981**, handles console status and returns the target exit code when available. **Verdict:** strongest inspected procgov capability is normal pre-associated native limit launch. **FAIL** as a complete strict automatic resource manager or unconditional crash owner. **CONDITIONAL** as the ready launch primitive in a narrower controlled combination. ## 8. Native Windows option: sufficient at the manual level, not an automatic policy

[Task Scheduler instance policy](https://learn.microsoft.com/en-us/windows/win32/taskschd/taskschedulerschema-multipleinstancespolicy-settingstype-element) controls instances **of a task**, not arbitrary tasks sharing RAM. Queue, IgnoreNew, Parallel and StopExisting have distinct semantics. IgnoreNew may discard an additional start rather than preserve a pending job; a per-task Queue is not a bounded general job ledger.

[Task Scheduler result constants](https://learn.microsoft.com/en-us/windows/win32/taskschd/task-scheduler-error-and-success-constants) distinguish ready/running/queued/terminated/constraint failures. A successful API call or Last Run Result is not proof of model unload, tree cleanup, a required cap or a remote result receipt. A stopped task is not proof an independently running model daemon stopped.

Idle/battery/user-session constraints are useful ready controls. [Idle-condition documentation](https://learn.microsoft.com/en-us/windows/win32/taskschd/task-idle-conditions) has version-specific and deprecated UI settings; an idle trigger is not a live physical/commit admission budget. Do not turn old Windows 7/8 timing descriptions into a measured Windows 11 rule.

PowerShell 7 is not Windows PowerShell 5.1 already bundled with Windows. Neither needs to be installed for manual native observation. A new script that calculates thresholds/leases is code, not “configuration only”.

- [Start-Process](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.management/start-process) can wait for a process and descendants on Windows; Wait-Process is narrower. Waiting is not required-cap setup or owner-crash cleanup.
- [RunspacePool](https://learn.microsoft.com/en-us/dotnet/api/system.management.automation.runspaces.runspacepool) bounds concurrent runspaces; same-process script concurrency is not independent per-script OS memory containment.
- [.NET Process.Kill](https://learn.microsoft.com/en-us/dotnet/api/system.diagnostics.process.kill?view=net-10.0) with entireProcessTree requests tree termination, but HasExited/WaitForExit can report the root exited while descendants remain; inaccessible descendants can be skipped. A new C# host must not mistake this for Job ownership.
- Windows native Job APIs provide primitives, not a prebuilt durable admission controller.

**Answer:** ordinary-user, on-demand management with native observer windows and deliberate human start/stop is the smallest real ready environment for manual use. No permanently resident UI, workflow server, AI or new program is necessary for that level. Its safety depends on human scope and supervision; no strict automatic policy is claimed.

The [Go minimum requirements](https://go.dev/wiki/MinimumRequirements) support Windows10+ for modern Go; the [Rust platform support table](https://doc.rust-lang.org/rustc/platform-support.html) lists x86_64-pc-windows-msvc as Tier1 with host tools. Neither choice requires a VM/WSL for a native core. Building needs the respective compiler/toolchain and selected native-link/UI dependencies; a properly packaged runnable binary does not imply installing the compiler on the target. These facts support feasibility, not a measured memory ranking. A failed Rust target-specific page was recovered through the official aggregate table.

### 10.2 Lifecycle and rollback

Prefer ordinary-user on-demand operation for these comparisons. Startup at login, service registration or running as SYSTEM requires separate justification/authorization. A logged-out/sleeping/off laptop cannot promise local service availability; a separate powered host is a different decision.

Future rollback means stop admitting work, cancel/confirm only owned work, stop the chosen manager, preserve history/artifacts, then remove only the specifically approved startup/task/service entries. Do not kill unrelated PowerShell/browser processes, delete model/state files, disable Windows services or shut down unrelated WSL instances as a generic cleanup method. No rollback actions were needed or executed in this research.

## 11. Is a “tiny adapter” actually small?

### 11.1 Responsibility map

| Responsibility | Existing ready mechanism | Missing application policy | When it becomes new controller work |
|---|---|---|---|
| Durable pending/run queue | Dagu existing store and CLI/REST | Map accepted item to one authoritative run identity | Adapter creates a second independent scheduler/pending queue |
| Host readings | Native APIs / ready observer | Freshness, error handling, reserve and unknown-peak rule | New heavy metrics service/ETW pipeline without need |
| One global heavy lease | No complete ready cross-product mechanism proven | One serialized grant/release/reconcile authority | Separate daemon/database lock managers added |
| Native caps and ordinary launch | procgov or ProcessKit ready runner | Exact required scope, args, status interpretation | Adapter must implement atomic creation, handles/nesting and failed-start cleanup itself |
| Mandatory control availability | Ready runner has useful IPC but fallback gaps | Refuse if required channel/receipt unavailable | Requires patch/native launch barrier or custom worker handshake before useful work |
| Model lifecycle | One server's load/status/unload APIs | Global lease, allowed configuration, bypass control and release proof | Adapter becomes a second general model router/backend manager |
| Cancellation and release | Runner/engine commands | Correlate completion, remaining/unknown state and lease | Multiple competing stop owners, PID/name scanning and unsafe cleanup |
| Durable receipt/recovery | Dagu history or runner JSONL | Commit acceptance, transition identity and unknown outcomes | Adapter invents a second canonical job/approval/result store |
| Operator status | Ready UI/CLI | Explain HOLD, lease owner, errors and controlled override | Permanent custom chart/browser stack before semantics are justified |
| Permissions/input contract | OS identity / narrow pipes | Approved executable/args/artifacts, bounded rights/resources | Arbitrary plugins/shell/credential distribution architecture |

A policy adapter is **narrow only if** Dagu remains the sole pending/run authority, the runner satisfies the accepted lifecycle contract, no mandatory pre-execution channel gap remains, and the adapter owns only bounded admission/lease metadata plus exact API translation. It may need a small transactionally stored lease/reconciliation record; that is not a license to copy Dagu's entire queue or declare a new authority.

If it needs its own scheduler, durable pending queue, Job creation, IPC security, approval engine and recovery state machine, **R1b is a substantial new controller**. In that case compare a single M4 host directly. Do not award R1b a high “ready” score for software that does not exist.

### 11.2 Smallest honest future contract, without code/schema

The minimum responsibility is to accept a bounded declared local job, check identity/permissions and evidenced resource envelope, read fresh host state, acquire the single heavy lease, invoke a qualified owned launch, observe readiness/result/cleanup, and persist enough state to reconcile after interruption. Unknown metrics/peak/ownership means HOLD with a visible reason.

No universal registry framework is needed. The future declaration needs executable/interface identity, bounded inputs/outputs, allowed working/artifact locations, rights/network scope, resource evidence and timeout/cancel behavior. No manifest or format is authored here.

Admission checks and launch are not atomically tied to the entire host OS: an unrelated browser can allocate immediately afterward. Native caps plus pressure reaction reduce risk; they do not create a physical RAM reservation. User override cannot silently turn unknown scope into safe execution.

For policy-only integration, a ready runner remains preferable to rewriting FFI. For the stronger creation-time + kill-on-close + required-management-before-execution contract, neither reviewed ready procgov nor ProcessKit proves the whole conjunction. A native implementation might be justified **only after that stronger requirement is chosen**, not simply because the word controller appears in the goal.

### 12.1 llama.cpp: sleep, unload request and confirmed exit are different

The tagged [server README](https://github.com/ggml-org/llama.cpp/blob/v0.7.0/tools/server/README.md) and [server-models.cpp](https://github.com/ggml-org/llama.cpp/blob/v0.7.0/tools/server/server-models.cpp) were read, not just an OpenAI-compatible endpoint description. The router's default maximum loaded-model count is **4**; **0 means unlimited**, not disabled. Automatic model loading is enabled; idle-sleep defaults to disabled. A sleeping child remains running and can wake on another request.

A new source-level distinction closes an A0011 ambiguity: the ordinary running-model unload path requests the child stop and returns while the monitor changes its status. The broader unload-all path separately waits for children and has its own deadline/kill logic. Therefore **a successful unload HTTP response is not by itself proof that a particular worker has exited or that host capacity is available**. A future adapter must observe the relevant terminal model/worker state, correlate OS ownership and then re-read host resources. It must not release a lease merely because sleep or unload was requested. **S/J**, not a measured reclaim claim.

Release provenance caveat: the official latest stable metadata identifies v0.7.0, but that release entry exposed only **nightly-tag.txt** as its asset in this inspection. Tagged source semantics are verified; a runnable Windows archive matched to those semantics is **U** here. Do not silently equate a changing nightly binary with the reviewed tag.

### 12.2 Ollama: retention and queueing are model-local mechanisms

Tagged [configuration](https://github.com/ollama/ollama/blob/v0.40.6/envconfig/config.go) and [scheduler](https://github.com/ollama/ollama/blob/v0.40.6/server/sched.go), together with the [official FAQ](https://docs.ollama.com/faq), distinguish:

- Default retention is **5 minutes**; zero requests no retention and negative retention is indefinite. Per-request session duration can override the configured default and affect reused runners.
- Default parallel setting is **1**, but maximum loaded models uses automatic selection when its environment value is zero; inspected scheduler logic includes a default models-per-GPU factor of **3** and does not mean one universally.
- The default pending request bound is **512**. This is an inference queue, not a cross-product host admission lease or durable external-action workflow.
- Loaded-model status and explicit unload are useful; scheduler removal calls the runner close path. Neither that operation nor its GPU-memory recovery observation is a whole-system physical/commit guarantee.

The release notes mention an orphan-runner fix; this is a publisher change record, not proof that every owner-crash condition is fixed on the laptop. This Ryzen/Vega device must not be declared supported for modern GPU offload from an old FAQ's ROCm paragraph. CPU-only feasibility, accelerator support and actual benefit all remain separate **U** questions; none is required to choose the empty manager.

### 12.3 Lemonade: pool semantics, worker visibility, and the prefix conflict resolved

Read tagged [multi-model documentation](https://github.com/lemonade-sdk/lemonade/blob/v2026.42.1/docs/guide/configuration/multi-model.md), [API guide](https://github.com/lemonade-sdk/lemonade/blob/v2026.42.1/docs/api/lemonade.md) and [actual route registration](https://github.com/lemonade-sdk/lemonade/blob/v2026.42.1/src/cpp/server/server.cpp).

Default max-loaded-models is **one per type**, not one across every type. Routing helper pools are separate; classifier/router use can add warm residency. Dynamic idle-VRAM eviction is opt-in, not a default physical-RAM policy. Pinned or busy workers may prevent eviction, and a llama.cpp soft-downsize path is a no-op in the reviewed documentation.

The health API's loaded-model records include **pid, launch_command, backend_url, type and pinned state**. This is useful process correlation, not independent OS attestation. Unload can target a model or all models; the Lemonade server remains resident. System statistics alone do not implement admission.

The API guide examples use **/v1/**, while other documentation uses **/api/v1/**. Source inspection resolved this apparent conflict: the route-registration helpers register both prefixes, as well as legacy v0 variants, for load/unload and other shared endpoints. Thus this is a documented/source alias distinction, **not an unresolved route guess**. Still pin the actual server binary and version before any later integration. No request was sent to a running server.

### 12.4 llama-swap: do not add a second manager automatically

The tagged [entry point](https://github.com/mostlygeek/llama-swap/blob/v265/llama-swap.go) treats failure of its platform tree-cleanup setup as a warning, not a mandatory refusal. The Windows tree-cleanup source provides a kill-on-close Job mechanism where successful, but configuration/startup success cannot be assumed from the presence of that code.

TTL zero means never automatically unload at the relevant setting; inheritance and per-model overrides are distinct. Explicit unload routes and status are useful, but advanced configurations can keep more than one worker. This may be useful when the selected engine lacks an adequate lifecycle API; it is unnecessary duplication when the engine already supplies the needed router/load/unload controls. One HTTP address is not one worker, one lease or one RAM budget.

### 12.5 LM Studio llmster: exact instance IDs and daemon identity

Official [headless operation](https://lmstudio.ai/docs/developer/core/headless), [TTL/eviction](https://lmstudio.ai/docs/developer/core/ttl-and-auto-evict), [load](https://lmstudio.ai/docs/developer/rest/load), [unload](https://lmstudio.ai/docs/developer/rest/unload), [daemon CLI](https://lmstudio.ai/docs/cli/daemon/daemon-up) and [terms](https://lmstudio.ai/terms) were rechecked.

The REST load endpoint **POST /api/v1/models/load** returns an **instance_id** and loaded status; **POST /api/v1/models/unload** acts on that instance ID. This is different from passing a generic downloaded model identifier to an OpenAI-compatible endpoint. When JIT is enabled, a model listing can include downloaded but unloaded models; listing is not sufficient loaded-state proof.

JIT default idle TTL is **60 minutes**; default auto-eviction is scoped to JIT-loaded models. Explicitly loaded non-JIT models are not automatically covered by that assumption. Headless llmster avoids requiring the desktop UI. The daemon CLI can report PID/status/version; its documentation's example version is not the current installed or latest daemon version. Desktop 0.4.26 does not close that independent version gap. Closing the visible GUI can leave a tray/background process running.

Terms permit personal/internal business use under conditions; the proprietary software must not be treated as a freely redistributable SaaS component. Native/local use and optional online functionality have different privacy/network implications. Any future adapter should use the actual lifecycle API, not GUI automation where a stable API exists.

### 12.6 The minimum lifecycle evidence needed before releasing a heavy lease

“Ready to use” means the intended loaded instance has passed the engine's readiness signal, not just that a TCP port is open. “Finished” means requests are drained/cancelled, owned workers are in the agreed stopped/unloaded state, native cleanup reports no unknown remainder and fresh host readings are acceptable. A resident manager may be allowed by explicit policy; it must remain visible in the accounting.

An engine launched outside the chosen owner, a second GUI-launched daemon, an independent client triggering autoload, a pinned helper or a sleeping-but-resident worker can bypass the intended global rule. Ordinary-user setup does not magically prevent every local client bypass. A future accepted scope must either control those entry points or admit that enforcement is supervised. No universal ready product reviewed here proves exclusive ownership across all five engines and unrelated applications.

## 13. Real resource-aware admission on this laptop

### 13.1 Historical constraints, not new measurements or arbitrary thresholds

The original Windows Journal records **Lenovo81W1 / IdeaPad 3 15ADA05, Ryzen 5 3500U / Vega 8, Windows 11 Pro, 8 GiB physically installed, about 5.88 GiB OS-visible and about 2.1 GiB hardware reserved**. Historical ordinary available physical memory was about **2–3 GiB**, varying with foreground activity. These are **H**, not current readings.

Historical commit readings around **4.3–4.66 / 7.5 GiB** describe then-current system commit. The recorded system-managed pagefile's **1664 MiB allocation was not a promise of a fixed maximum**. A growing pagefile can raise commit capacity; it does not create physical RAM or remove latency risk.

The UMA preallocation is already taken from installed RAM. A displayed shared-GPU memory capacity is not another equally sized permanent reservation to subtract again. Mapped GGUF pages, file cache, private allocations, driver memory and VRAM/UMA must be accounted for in their actual categories rather than added as if all were exclusive private heaps.

The [Lenovo family PSREF](https://psref.lenovo.com/syspool/Sys/PDF/IdeaPad/IdeaPad_3_15ADA05/IdeaPad_3_15ADA05_Spec.pdf) describes soldered-plus-slot configurations, including family offerings up to 12 GB. It is not verification of this unit's serviceable slot/module or permission to buy RAM. No hardware purchase, BIOS/UMA alteration or upgrade recommendation is necessary for this research decision.

### 13.2 What the relevant Windows measurements mean

| Signal | Appropriate use | Must not be inferred |
|---|---|---|
| Available physical memory from [GlobalMemoryStatusEx](https://learn.microsoft.com/en-us/windows/win32/api/sysinfoapi/nf-sysinfoapi-globalmemorystatusex) / native performance information | Present reclaimable/available physical capacity, including eligible standby pages; trend with ordinary foreground use | Installed RAM or free-list-only bytes are the usable budget |
| [PERFORMANCE_INFORMATION](https://learn.microsoft.com/en-us/windows/win32/api/psapi/ns-psapi-performance_information) CommitTotal, CommitLimit and PageSize | System commit headroom in consistent units; observe changing limit/headroom | Pagefile size alone equals headroom, or headroom equals physical RAM |
| [Low/high memory-resource notification](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-creatememoryresourcenotification) and [query result](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-querymemoryresourcenotification) | OS physical-memory pressure signal with a neutral range; useful reaction input | No low event means sufficient commit; failed query means safe |
| Owned Job/current processes plus [PROCESS_MEMORY_COUNTERS_EX](https://learn.microsoft.com/en-us/windows/win32/api/psapi/ns-psapi-process_memory_counters_ex) | Scope/identity, private commit and working-set observations with known meanings | PrivateUsage/PagefileUsage is simply bytes currently swapped to disk |
| [Job extended limits](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_extended_limit_information) | Enforce process/aggregate Job commit limits as specified | A physical RAM reservation or forced complete reclaim |
| CPU rate, foreground responsiveness and paging trend | Decide whether further work is tolerable; correlate sustained pressure over time | Low CPU alone means memory safe; every hard fault is a pagefile read |

**J:** combine physical headroom, commit headroom, observed task envelope and foreground tolerance. They answer different questions; neither replaces the other. Hard faults can involve mapped executable/model/file pages as well as pagefile-backed data, so a count alone does not identify pagefile thrashing. Short bursts, sustained I/O, user latency and pressure must be interpreted together.

A small native observer can query these APIs in the existing session without a full-time browser, metrics database or new ETW service. PDH/ETW are optional diagnostic facilities, not ready policy. Reading counters is the easy part; validating error/status, unit, timestamp, scope and decision ownership is the missing application behavior. No monitoring program was created.

### 13.3 Admission contract and honest limits

A future automatic owner needs all of the following human-readable rules. This is a contract discussion, not runnable pseudocode:

- **Unknown workload peak or hidden worker scope ⇒ QUEUE/HOLD.** Weight-file size, a guessed context size or a vendor “8 GB supported” badge is not an observed task envelope. Future bounded qualification can establish an envelope; this report cannot invent one.
- **Stale, failed, unsupported, inaccessible or contradictory readings ⇒ HOLD**, with the missing signal shown. A last good number is not silently treated as current.
- **One shared heavy lease across all queues and relevant engine pools.** Per-DAG concurrency, per-model queueing and independent scheduled tasks cannot each grant the same capacity. One owner serializes admission and reconciliation.
- **Fresh checks near launch and continued pressure monitoring.** A precondition measured earlier is not a resource reservation. An unrelated application can allocate immediately afterward.
- **CPU/foreground control is explicit.** Hard CPU-time cap, affinity, priority and background mode differ. A low priority or fewer selected cores may help responsiveness but is not a numeric whole-host cap. Nested Job percentages must be interpreted in their actual parent-relative context.
- **Fairness without unsafe admission.** A waiting item may age, change priority, be cancelled or be reported as blocked; it does not eventually bypass missing capacity simply to avoid starvation. Bounded queue size, waiting visibility and deliberate cancellation are part of the contract.
- **Pressure response owns its consequences.** Refuse new work first; request supported graceful release of owned idle workers; escalate only within authorized contained scope. Unknown cleanup keeps capacity held/blocked. Killing unrelated processes, trimming all working sets or emptying standby lists is not a valid automatic fallback.

The threshold/envelope/reserve must be agreed from later representative evidence and user tolerance, not a universal fixed MB number. The review does not prescribe pagefile, registry, BIOS, driver, UMA or power-plan changes. It does not promise that eight installed GiB can host an unbounded local model.

### 13.4 What can be ready-configured, and what is still missing

Ready components supply observation, queueing, native caps, model unload and operator interfaces. They can also supply timeouts and limited task-instance policies. They do **not collectively prove** one atomic decision over fresh host physical/commit state, evidenced workload peak, cross-queue/model lease, required control-channel availability and crash reconciliation.

At the **manual level**, the operator supplies that decision. At the **best-effort automated level**, preconditions and limits supply useful partial protection. At the requested **strict automatic level**, the missing part is policy ownership and lifecycle reconciliation, not a magic RAM-freeing command. It may be a narrow integration only if the ready runner's accepted limitations fit the requirement. If the requirement rejects those limitations, the native launch/control boundary is also new work.
