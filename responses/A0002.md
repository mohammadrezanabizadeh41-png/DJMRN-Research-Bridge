# Part A — Discriminating A/C Study

## 3. What is actually being compared

### A — existing Windows scheduling plus a small on-demand worker

**Proposed composition:** native Task Scheduler starts one bounded deterministic worker, with a local transactional domain ledger and evidence files. Python 3.14.7/standard-library SQLite is a comparison implementation because it has a narrow prior witness, not a chosen architecture. No model, browser, external API, web server, or permanent DJMRN daemon is needed for the future offline fixture.

**Source facts:** Task Scheduler is installed with supported Windows versions and provides GUI/API scheduling. Its GUI manages scheduled tasks, not DJMRN's versioned-draft review. Python's SQLite interface uses a disk database without a separate database server; transaction behavior must be explicit. Current online Python 3.14 docs identify themselves as 3.14.8; that does not update the user's reported 3.14.7 installation. [Windows](https://learn.microsoft.com/en-us/windows/win32/taskschd/about-the-task-scheduler), [Python SQLite](https://docs.python.org/3.14/library/sqlite3.html)

**Lifecycle DESIGN:** receive and persist work; leave a durable pending-review state; exit. A later separately authorized user command records approval; a later invocation verifies it and performs or reconciles the bounded operation. Do not keep a Python process blocked for days waiting for a person. Task Scheduler's overlap setting is not job-level deduplication: IgnoreNew ignores overlapping triggers, Queue queues task instances, and neither supplies the original notification payload as a durable inbox. Persist intake before relying on a later run. [MultipleInstancesPolicy](https://learn.microsoft.com/en-us/windows/win32/taskschd/taskschedulerschema-multipleinstancespolicy-settingstype-element)

### C — Dagu 2.21.0 plus application-owned effect state

**Source-pinned target:** [Dagu v2.21.0](https://github.com/dagucloud/dagu/releases/tag/v2.21.0), not a claim that every live-doc capability is frozen to that release. The pinned `README_SCHEMA.md` was retrieved, blob SHA `709a7440358ba30c2d4472e41e6aa96d50eccdf6`, and confirms command-free `human.task`, root-DAG placement and typed scalar form inputs. Pinned `LICENSING.md` SHA: `1ff532ce1d120bb7d2c4ceae8870f92d44e58b65`.

**Source facts:** the single-server topology combines server/UI, scheduler and execution engine; command steps can still create child processes. It uses local run/history/log files without an external DBMS. Prebuilt use does not require installing the Go compiler. The pinned source-build `go.mod` requests Go 1.27.2, which is a source-build requirement, not an extra runtime service. The pinned Windows installer script references WinSW v2.12.0 for service setup. Manual user-session binary execution avoids that optional service installation. [Deployment models](https://docs.dagu.sh/overview/deployment-models), [go.mod](https://github.com/dagucloud/dagu/blob/v2.21.0/go.mod), [installer](https://github.com/dagucloud/dagu/blob/v2.21.0/scripts/installer.ps1)

**Current-doc facts:** completing a Human Task records input and queues resumption; it does not itself launch downstream work. A scheduler must be available to pick up queued continuation. Identical completion input is idempotent; different repeated input conflicts. These are workflow-completion semantics, not portal-send guarantees. Current docs also describe recovery when input was saved but queueing failed. Release-specific behavior still needs the future fixture. [Human Tasks](https://docs.dagu.sh/writing-workflows/human-tasks)

**Scope reduction:** no distributed workers, hosted Console, public webhooks, MCP control, AI steps, containers or downloaded third-party actions are required for this comparison.

### Approval boundary

A proposed approved intent contains stable references to: operation, account/site, thread or Notion target, exact versioned draft/diff, recipient, attachment hashes, source snapshot, approver identity, policy version and expiry. Preserve raw text alongside a reproducible digest; do not normalize meaningful message content invisibly. A trusted gate rechecks the approved payload and source immediately before the effect.

This binds permission to what was reviewed; it does **not** eliminate a source-change race between the last read and the remote write. Use server-side conditional revisions/idempotency only where the actual platform supports them. Neither a generic browser nor this research establishes such support. For platforms without it, residual concurrency risk must be presented to the user and may require a final user-present check.

### Dagu approval placement and bypass risks

[Approval Gates](https://docs.dagu.sh/writing-workflows/approval) documents that an attached executable runs before review. Therefore:

- Use preparation, then a separate command-free Human Task, then an independently guarded action.
- Do not put attached approval on SEND or on a child workflow that already sends.
- A skipped/continued review step or missing artifact must never enable the action. The worker requires the actual current authorization, not just upstream “success.”
- Do not interpolate reviewer text into shell commands. Pass an opaque intent reference as an argument, validate typed input, and resolve the payload inside the worker.
- Dagu's form is a UI mechanism; it does not authorize a browser account, prove source freshness or clear an UNKNOWN effect.

The pinned schema explicitly permits review artifacts to be missing without blocking completion. Thus “artifact listed in the UI” cannot be the security invariant.

## 8. Smallest future offline synthetic acceptance fixture

**Design only — not permission to run P1-B, install Dagu, create schedules or change Windows settings.**

### Contents and isolation

Use one synthetic B job and one synthetic C proposal, with resettable snapshots per case. A fake portal and fake Notion are **local data files/oracles**, not real websites and not network servers. No account, browser, model, provider, email, private data or cloud is needed.

The fixture contains: immutable source/draft revisions; a domain ledger; a trusted synthetic approval input; a separate fake-remote effect log; a controlled clock value; and expected-result records. Keeping the fake-remote log separate deliberately exposes the crash window between “remote accepted” and “local ACK stored.” The simulator must expose the true effect count to the evaluator; the worker sees only permitted reconcile responses.

The same domain adapter and test data should be driven first by A, then by C only if separately approved. Differences should be orchestration/review mechanics, not different safety logic. This avoids crediting Dagu for a better custom worker.

### Acceptance cases, parameterized for B and C

| Case | Injection | Expected durable result / oracle |
|---|---|---|
| F1 | Same intake delivered twice | Same job/receipt; one logical intent |
| F2 | Same intake key, changed payload | Conflict; no new effect |
| F3 | No approval / forged model-provided approval | Refused; fake-remote effect count 0 |
| F4 | Draft/recipient/attachment/target changed after approval | Stale approval rejected; effect count 0 |
| F5 | Approved source revision changes | Review reopened; effect count 0 |
| F6 | Worker killed before attempt commit | Recoverable pending state; no remote call yet |
| F7 | Kill after attempt commit, before fake remote accepts | UNKNOWN until simulator-provided reconcile evidence resolves it; no blind second call |
| F8 | Fake remote commits, ACK lost | UNKNOWN, then confirmed from read-only evidence; exactly one observed fake effect |
| F9 | Reconcile response ambiguous/partial | Remain blocked with human reason; no additional effect |
| F10 | Duplicate/conflicting completion, missing review artifact, or two overlapping workers | No bypass; conflict/hold where required; no duplicate effect |
| F11 | Process restart while waiting / after saved approval | Approved payload remains immutable; correct job resumes without developer reconstructing it |
| F12 | C proposal partly applied at fake target | Detect partial result; no re-append of already applied content; no false DONE |

These **24 parameterized cases** are a proposed small test inventory, not a statistic about prior tests. It is permissible to implement only the minimal common fixture first; no requirement to create a generalized framework.

### Meaningful gates

Hard failure thresholds: **zero** unauthorized effects; **zero** duplicate fake effects; **zero** stale approvals accepted; **zero** fabricated source/readback receipts; **zero** lost acknowledged intake records; **zero** false CONFIRMED/DONE states. Any breach stops the candidate. All cases must match their explicit expected state, including cases expected to remain blocked.

Keep liveness distinct from safety: stopping forever prevents duplicates but is not a usable capability. A normal approved case must finish; an UNKNOWN case must lead to a visible reconcile/review action with enough retained information for the user. Measure reviewer actions, reconstruction effort, recovery after restart, process trees, idle residue, wall time, working set/private commit, whole-system available/commit and power state. These measurements are **NOT RUN**.

A0001's numeric resource thresholds were hypotheses, not known safe laptop capacities. Do not carry them forward as acceptance facts. Before any future run, agree a foreground responsiveness/memory safety budget from a fresh read-only baseline. Power-loss and real sleep/battery tests remain later independent gates; a subprocess kill does not simulate all storage/power failure modes.

### What would falsify the need for Dagu?

**Predeclared JUDGMENT tests:** if A passes the same safety/restart cases, gives the user adequate review/recovery without developer intervention, and the real use case has no demonstrated need for Dagu's ready run UI or multi-step waits, then Dagu is unnecessary for that vertical. Also reject/defer C if required governance features cross a paid boundary, user-session operation is unsuitable, state recovery cannot be demonstrated, idle/lifecycle cost violates the agreed budget, or custom effect/authorization code is not reduced in a way the user values.

Conversely, a real usability gap in A—such as repeatedly reconstructing pending decisions or building a significant review/run-history interface—would be evidence for evaluating C. It would not authorize deployment automatically.
