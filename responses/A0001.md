## 1. Executive result

No architecture family earns selection from this research. Four concrete bundles can be compared against the same receipt, approval, external-effect, restart, and evidence fixtures:

- **A — small Windows-first controller:** Windows Task Scheduler + one-shot Python worker + SQLite ledger + on-demand browser/model child processes. This has the fewest required resident parts, but most domain safety and the approval UI remain custom.
- **B — ready agent framework:** LangGraph 1.2.13 + SQLite checkpointing + a small local review surface. It supplies resumable graph state and interrupts; it does not supply DJMRN's exact approval digest, portal reconciliation, or safe external-effect semantics.
- **C — durable workflow runtime:** Dagu 2.21.0 on Windows, using its local state and Human Task step before a separately gated effect. It offers the clearest ready workflow UI among the compared local bundles, but its run history is not a portal receipt and a separate domain-level effect ledger remains necessary.
- **D — ready desktop AI application:** AnythingLLM Desktop 1.18.0 + built-in Lemonade local inference + optional MCP/Agent Skills. It is a newly surfaced app-first candidate. It can provide a usable chat/agent surface, but it is not a durable workflow or authority system; computer-use is documented as beta and should not receive an authenticated send capability.

A is the smallest comparison baseline, not a proven winner. C is the strongest ready workflow surface in this comparison, not a complete B/C copilot. D is an app-first alternative for low-risk, user-present tasks, not for unattended portal action. Every candidate remains **RESEARCH ONLY**. No install, download, benchmark, provider call, account action, Notion edit, or P1-B execution occurred.

The main safety invariant is common to all four: persist a specific, reviewable intent before an external effect; bind approval to the exact account, portal thread, message/change digest, and freshness; after a timeout with a possible remote effect, record **UNKNOWN**, reconcile against the original portal, and never retry blindly. Framework retries, a green workflow step, a returned browser click, or a model response do not establish that a remote action happened exactly once.

Labels below mean:

## 4. Four concrete bundles

### A. Windows-first small controller, no agent framework

**Bundle:** Windows 11 Task Scheduler (built-in) + Python 3.14.7 one-shot worker (the version previously reported installed) + Python standard-library `sqlite3` ledger + a small Python Win32 Job Object wrapper for owned child processes. Add Playwright Python 1.64.0 only when an authorized browser capability is actually needed. No always-running DJMRN service is required for the first deterministic vertical.

- **Receipt / durable domain state:** worker writes an idempotent receipt and current job state into one local SQLite database under a user-owned project directory. Record source IDs, payload hashes, state versions, evidence references, and remote-effect status. Use SQLite transactions and the default rollback journal for the initial comparison; do not choose WAL merely by habit. The current SQLite library/version from the live Windows installation must be re-read before a real test.
- **Authorization:** custom review surface, initially a human-readable pending-intent file/console or a minimal local UI. Approval record binds the exact user, portal/account, thread/page, action, digest, attachment manifest, observed source version, policy version, and expiry. The worker verifies the digest immediately before the action. A console-only gate is less usable and is not a finished product.
- **External effect / UNKNOWN:** custom state machine in the domain ledger: `PREPARED → APPROVED → ATTEMPTING → CONFIRMED` or `UNKNOWN`. The one-shot worker exits after each unit; on restart it resumes by stable job/effect ID. For `UNKNOWN`, a separate read-only reconciliation worker checks the original site before any human-authorized retry.
- **Model / provider:** provider registry is explicit allowlist configuration owned by the controller; starts with **no provider selected**. Deterministic validation precedes a model call. If later tested, the engine is a replaceable child/provider adapter; do not let model output choose a provider or receive account credentials.
- **Worker/process lifecycle:** Task Scheduler starts the controller on demand or on a named schedule. The controller starts a browser or inference process only for a bounded stage and requests termination when done. Job Objects can account/limit a process family and kill owned children when the last job handle closes; they are not a security sandbox and do not provide a physical-RAM/VRAM guarantee. Browser and model loading remain separate resource pools.
- **Evidence / cache:** source evidence is immutable/referenced by URL, capture time, hash, partial/stale marker, and claim; SQLite rows are workflow/domain state, not Notion's canonical architecture record. A read-only local mirror can be postponed.
- **UI:** existing desktop shell or a custom small local review UI; no prebuilt durable approval UI in this baseline.
- **License / cost:** Task Scheduler is included with Windows; Python is PSF-licensed, SQLite is public domain, and Playwright is Apache-2.0. Local execution has no per-request provider cost. Browser package installation and browser binaries would be separate downloads and are **not authorized here**. Exact Python 3.14 compatibility of a future Playwright build is not established by the inspected version pages and must be checked before selecting it.
- **Unresolved responsibility:** most code is DJMRN-owned: transaction and dedup rules, approval UI, secret-safe logs, idempotency, resource admission, source evidence, recovery, observability, test and upgrade process.

**Simpler sub-baseline:** Task Scheduler + one-shot worker + SQLite only, with no model, browser, resident daemon, agent framework, vector database, or new service. It is enough to test receipts and restart/reconciliation using synthetic inputs after separate authorization. It cannot execute the full B/C product cases by itself.

### B. Agent framework with separate governed state

**Bundle:** LangGraph OSS 1.2.13 + `langgraph-checkpoint-sqlite` (version must be frozen in a lockfile during any separately authorized pilot) + a small local reviewer UI/CLI + the same narrow Playwright worker adapter when required. Run the graph as an on-demand Python process; do not use LangSmith hosted services in this local comparison.

- **Receipt / durable state:** a coordinator-defined thread/run ID links LangGraph checkpoint state to the separate domain ledger. Checkpoint state is recovery state, not the canonical remote-effect receipt. Keep source evidence and external-effect IDs in the domain ledger; do not assume checkpoint replay means the action did not happen.
- **Authorization:** LangGraph `interrupt()` can pause and resume with a checkpointer. Build a distinct approval object and UI: interruption alone does not bind permission to the exact account/thread/digest or enforce expiry. Put the interrupt in a review node before the send node. LangGraph docs warn that a node interrupted/resumed can be re-run from its beginning; external side effects in a node before the interrupt, or non-idempotent effects on replay, are unsafe.
- **External effect / UNKNOWN:** separate effect-intent/status table and reconciliation adapter remain custom. On restart or replay, branch on persisted effect state and inspect the original site when state is UNKNOWN; never place the live SEND call in a node that may be replayed without a guard.
- **Model / provider:** deterministic graph routing and an explicit model adapter selected by controller policy. LangGraph itself is not an inference engine. Keep local/remote choice outside model output. Local inference could be reached via a separately qualified OpenAI-compatible API.
- **Worker/process lifecycle:** one Python graph worker can start on demand and persist between invocations through SQLite checkpoints. Local inference and browser children need independent timeouts, quotas, termination, and crash cleanup. Python package metadata inspected for current LangGraph lists Python classifiers through 3.13, while user’s reported Python is 3.14.7. **Python 3.14 compatibility is unverified**; either verify directly before use or compare a supported Python runtime as a separate dependency, not assume the existing interpreter works.
- **Evidence / cache:** checkpointed references to evidence, not a vector database by default. Notion remains canonical; an index is derived, read-only, and rebuildable.
- **UI:** no complete free local reviewer UI is included in the OSS runtime. LangGraph Studio/hosted LangSmith capabilities are separate products/terms; do not treat them as free or region-eligible by implication. The first comparison can use a local CLI but that is less usable.
- **License / cost:** LangGraph core is MIT-licensed and has no per-call charge when run locally. Optional LangSmith/hosted deployment, model provider, and model-weight terms are separate. No hosted option was invoked.
- **Unresolved responsibility:** domain state, exact authorization, remote reconciliation, browser restrictions, provider policy, process/resource control, UI, evidence provenance, secrets, and operations remain DJMRN responsibilities.

**Use only if:** a graph with multiple durable waits, conditional branches, and reviewed resume semantics is needed enough to justify framework dependencies and a second state representation. The Work-37 priority does not prove that this complexity is required.

### C. Durable workflow runtime, Dagu

**Bundle:** Dagu v2.21.0 (Windows release asset published 2026-10-18) + local file-backed Dagu run/state directory + YAML DAGs + one-shot Python/Playwright worker steps. For the first Windows comparison, run as a user-level app/service; official installer can register a Windows service via WinSW, but service installation is not part of this report.

- **Receipt / durable state:** Dagu owns workflow run, dependency, wait, and step-attempt state in its local data directory. A DJMRN domain ledger must still own deduplicated job identity, exact approved intent, evidence references, and site-effect UNKNOWN/confirmation. These two stores have different semantics; do not present Dagu run history as proof of a portal message.
- **Authorization:** use a root-DAG **Human Task** step before SEND to wait without executing a command. Do not attach an approval gate to the SEND step: Dagu's docs say an approval gate pauses after the attached executable step has succeeded. Dagu provides UI/API completion for human tasks; the reviewer and workflow still need to verify exact digest, site/account/thread version, expiry, and policy. Clear persisted human inputs/decisions when the reviewed intent changes.
- **External effect / UNKNOWN:** custom narrow SEND step reads one approved intent ID and rechecks its digest. Persist ATTEMPTING before the click. A Dagu retry, rewind, push-back, or re-run after timeout can repeat a side effect unless the step consults the domain ledger and reconciles the portal. Workflow resume is not remote exactly-once.
- **Model / provider:** DAG configuration selects a fixed allowlisted adapter; model output cannot alter the provider or bypass a human task. Dagu can invoke scripts/actions but does not supply the model or user-specific provider legality.
- **Worker/process lifecycle:** the Dagu coordinator/UI is a persistent process if registered as a service; individual command and browser workers are steps that start and exit. Local run state persists. Dagu’s scheduler and Windows power behavior need an actual bounded test: a background service can consume idle memory, and wake-from-sleep is not the same as availability while the laptop is powered off or on a constrained battery.
- **Evidence / cache:** store evidence in a domain-owned directory with manifest/hash and retain only references in workflow outputs. Do not let DAG logs become the only evidence archive; redact sensitive user/customer data and cookies.
- **UI:** built-in local UI and Human Task forms are a real advantage for review and resumption. If exposed beyond localhost, authentication/access control and network binding become security gates.
- **License / cost:** Dagu core is GPL-3.0-or-later, self-hostable and has a single Windows binary; some self-host features/monitoring are license-key gated, and proprietary embedding/distribution has separate terms. Personal execution cost can be $0 excluding hardware/time, but license review is required before bundling/distributing in a commercial product. Optional hosted monitoring is not needed or authorized.
- **Unresolved responsibility:** DJMRN still owns the approval contract, site adapter, outbox, UNKNOWN reconciliation, domain state, provider policy, evidence, per-machine resource policy, secrets, and end-to-end safety tests.

**Use only if:** local human-waiting DAGs and a ready run UI materially reduce custom workflow/UI work. Otherwise Task Scheduler + a one-shot worker has fewer moving parts.

### D. Ready desktop app first, AnythingLLM Desktop

**Bundle:** AnythingLLM Desktop v1.18.0 x64 + built-in Lemonade local inference engine + optional MCP/Agent Skills. Current publisher docs describe Desktop as targeting Windows 11, with Windows 10+ x64 installer information; product OS edition and hardware fit must be checked on the actual user installation. Do not use its beta computer-use feature for real portal SEND.

- **Receipt / durable state:** the app persists chats, workspaces, and local vector data in its own storage. Treat that as app data only. It is not the DJMRN task/effect ledger, Notion authority, or evidence provenance ledger; avoid ingesting the full Applied library into its vector store during this comparison.
- **Authorization:** MCP/Agent Skills are extension points, not a trusted authorization boundary. Keep all write-capable portal tools absent. If the application is evaluated, expose only read-only synthetic/local tools. A separate approved-action service must own any future exact SEND authorization.
- **External effect / UNKNOWN:** app logs/chat history cannot establish whether a remote site accepted a send. A detached domain ledger plus site reconciliation remains required, so the app alone cannot meet B's core safety contract.
- **Model / provider:** built-in Lemonade engine is a local inference route; remote providers can be configured but are a separate data-egress and cost decision. Weight license is per model and not granted by AnythingLLM's MIT license.
- **Worker/process lifecycle:** Desktop includes an Electron-style GUI/server and a built-in inference-server path. **Source documents establish the built-in engine but not the exact Windows child-process tree or idle/termination behavior for this machine**; measure those before any adoption. The app may remain open between tasks, so resident RAM is likely higher than the Task Scheduler baseline (inference, not a measurement). Its app-specific unload behavior must be verified for the exact build/model.
- **Evidence / cache:** native local vector store (LanceDB in Desktop storage) can support app retrieval but creates another derived index. Its stale/partial/permission behavior needs explicit evaluation; it must not become a second canonical library.
- **UI:** strongest immediate desktop interaction among the four and supports MCP/Agent Skills. This improves low-risk user-present research/help, but does not supply the workflow contract or account authorization.
- **License / cost:** AnythingLLM core/self-hosted Desktop is MIT-licensed and no subscription is required for its local core. Optional hosted models/services and model weights have separate terms, quota, country eligibility, card/overage, and privacy requirements. The app may fetch CDN-hosted model assets during setup; fully offline operation requires preloading/controlling those assets.
- **Unresolved responsibility:** DJMRN owns exact approval, provenance, safe external effects, restart recovery, resource admission, model entitlement, local data protection, logs, and lifecycle tests.

**App-first comparison alternative:** this is more ready than a custom local UI for chatting and low-risk tools. It is not a substitute for the simplest scheduled worker or a durable effect ledger.

## 7. Windows resources, process lifecycle, and containment

### Distinctions that must stay separate

1. **Admission:** decide whether a new model, browser, or indexing job may start given measured current load and the foreground-user reserve.
2. **OS process accounting/limits:** constrain a process tree's CPU, commit, active processes, lifetime, or priority.
3. **Model residency:** load, TTL, auto-evict, and unload weights/KV state in the inference engine.
4. **Security isolation:** constrain filesystem, network, identity, secrets, and permitted actions.
5. **Approval:** authorize one exact external action.
6. **Browser/session lifecycle:** isolate site identity/context, cookies, downloads, and end the worker.

One control does not provide the others. In particular, a Job Object limit is not a security sandbox; a model-server TTL is not a whole-machine resource controller; a sandbox is not consent; a browser timeout cannot roll back a remote send.

### Windows facts and candidates

- **Task Scheduler (FACT):** Windows provides start-on-demand, restart-on-failure, and wake-to-run settings. Wake-to-run can wake a sleeping computer and keep it awake until task completion; it cannot run a laptop that is shut down. Battery, lid/sleep, network, and user-session behavior need a real test.
- **Job Objects (FACT):** Windows Job Objects can manage process trees and selected CPU/memory/time/priority limits. Closing the last handle with kill-on-close can terminate associated processes. Job commit limits are not a guaranteed resident-memory or GPU-memory envelope; nested jobs, assignment failures, breakaway, and privilege boundaries need explicit tests. A standard user may not be able to contain every process it did not create.
- **Process Governor (EXISTING-ENRICHMENT):** upstream `lowleveldesign/process-governor`, release line `4.1.26190` as already recorded in WORK-37. It wraps Job Object controls. Its install mode persists settings and creates a Windows service, a materially different trust/privilege model from a narrow per-process CLI. Keep it provisional and compare against direct native Job Objects; do not install or assume its service is harmless.
- **Microsoft MXC (EXISTING-ENRICHMENT / VERSION GATE):** upstream `microsoft/mxc`, v0.9.0 release family, is layered containment, not a resource scheduler or permission grant from an LLM. Current first-party OS support table retrieved here lists Windows 11 26H2 ProcessContainer and IsolationSession gates at build `26300.9550`; earlier WORK-37 text recorded an IsolationSession gate of `26340.9212`. This is a source/version disagreement to preserve and resolve against the exact release commit before any test. The user's prior base-build snapshot `26300` lacks the required UBR evidence; no compatibility claim is justified.
- **Inference engine example (EXISTING-ENRICHMENT):** LM Studio's official local API documents JIT loading, an idle model TTL, and auto-eviction of previous JIT-loaded models. Defaults documented: 60-minute idle TTL; auto-evict can keep at most one JIT-loaded model resident. Manual `lms load` with no TTL remains loaded until unload. This can manage model residency but not the browser or other apps. Local LM Studio is documented free for home/work; Bionic/cloud is a different optional service/plan.
- **Alternative local process model:** a pinned `llama.cpp` server process can be started and stopped as a child, but the GitHub release stream is rapidly moving; a Windows build/backend/model combo and actual memory release must be tested. Do not use the newest prerelease by default. No model, binary, or backend is selected here.
- **Browser isolation (FACT):** Playwright BrowserContexts provide isolated cookies/storage. Auth state saved to disk contains session credentials capable of impersonation; the publisher warns not to commit it. Use a narrowly scoped, user-approved profile; never put cookies, OTPs, or session files in GitHub, logs, prompt text, or public research storage.
- **Power/recovery (INFERENCE):** suspending retains process memory; killing children releases owned allocations only after OS exit/reclaim. On sleep, network loss, update/reboot, or battery-triggered stop, persist a checkpoint first; any in-flight remote effect becomes UNKNOWN and requires reconciliation. Dagu's persistent coordinator and a desktop app can remain resident when idle, which must be measured rather than assumed acceptable on S0.

No Windows limit, Job Object, MXC, Process Governor, browser, inference TTL, or battery-recovery test was run in this task.

## 8. Model, engine, provider, and benchmark design

### Separate layers

- **Weights:** exact publisher/repository/revision/hash, quantization, tokenizer, context, architecture, model license, commercial terms.
- **Inference engine:** version/build, CPU/GPU backend, offload, runtime settings, load/evict semantics.
- **Host:** Task Scheduler worker, LangGraph invocation, Dagu step, or desktop app.
- **Provider adapter:** local/remote API endpoint, credential and region rules, quota, data handling, error semantics.
- **Browser:** separate process/context, site permission, source snapshot, external effect.
- **Knowledge projection:** rebuildable, read-only index; not canonical state.

Initial comparison should use deterministic parsing/retrieval before model calls and at most one model resident per trial. A model engine cannot enforce approval or guarantee a browser effect. Model weights are individually licensed; permissive code licenses above do not establish commercial rights to a chosen model.

### Reproducible synthetic protocol — FUTURE ONLY, NOT RUN

Use one versioned corpus and identical input/output contracts for every bundle. Synthetic names, companies, emails, sites, and posts only; no private mail, actual customer data, real accounts, or live external actions. Record source commit, prompt, model revision, quantization, engine/backend, context, temperature/seed if available, and machine/power profile.

- **Persian structured extraction:** 24 synthetic CV/job/project/email records containing Persian and Latin text, mixed numeral forms, `ی/ي`, `ک/ك`, ZWNJ, RTL punctuation, and missing/conflicting fields. Score exact field accuracy, normalized-value accuracy, unsupported-field hallucination rate, and schema validity. Normalization applies to search/evaluation projections, never overwrites the original evidence.
- **Evidence-grounded research retrieval:** 30 questions over a fixed source set with exact page/version/hash and contradictory or partial records. Score Recall@5, MRR@10, citation-to-source correctness, claim support, stale-version detection, and explicit UNKNOWN behavior. Score lexical retrieval separately from model synthesis.
- **Python/JavaScript coding:** 20 synthetic bounded tasks per language with public and hidden unit tests, no network or shell access beyond a disposable fixture. Score test pass rate, scope changes, and reproducibility.
- **Instruction following / Farsi RTL:** 30 exact-output, refusal-boundary, formatting, and mixed-language instructions; score pass/fail per criterion, Unicode preservation, and unauthorized-action attempts.
- **B/C safety tabletop:** inject duplicate notifications, changed thread version after approval, expired approval, process crash before submit, timeout after possible submit, duplicate source page, partial capture, Notion update timeout, and changed proposal before review. Use fake portal/Notion responses only. Measure no duplicate effect, stale-approval rejection, UNKNOWN detection, restart recovery, reconcile correctness, and complete provenance.
- **Repeatability:** fixed temperature/seed where supported; minimum 5 warm-up calls and 20 measured samples per engine/workload, randomized architecture order, at least 3 complete runs. Report raw per-sample logs and configuration, not only averages. If a component is nondeterministic, show variance and error cases.

### Metrics and proposed stop thresholds

| Measure | Definition | Proposed hypothesis/stop gate (NOT device capacity) |
|---|---|---|
| Latency | wall-clock from receipt to each stage result; cold and warm; report p50/p95 | stop if interactive stage p95 > 60s or user foreground delay > 10s; thresholds need user review |
| RAM | process-tree working set and private commit; whole-system available RAM and commit/limit | stop before loading if available memory falls below 1.25 GiB or commit exceeds 85% for 30s; these are conservative test hypotheses, not tested safe values |
| GPU | dedicated and shared GPU memory per model/browser stage, CPU utilization | no fixed GPU limit until user S0 is measured; stop on device reset, sustained UI stall, or driver error |
| Idle residue | process tree + working set at 0/1/5 minutes after task, after unload/exit | any worker child left alive after bounded cleanup is a failure; app/server idle cost is reported separately |
| Correctness | task-specific exact/semantic scores and citation validity | no architecture passes if it fabricates source support or misses stale approval |
| Unauthorized effects | count of effects without a current exact approval | **0 allowed; one is an immediate fail** |
| Recovery | injected crash/restart + original-source reconcile | every UNKNOWN must remain blocked until reconciled; no blind resend |
| Dev/maintenance | setup steps, dependency count, code LOC by contract, upgrade/rollback/recovery steps | record rather than invent a score; reject a framework if it adds moving parts without reducing measured gaps |

Thresholds require authorization and recalibration after a read-only baseline; no laptop capacity is inferred from model file size or available-memory snapshots.

## 10. Risks and failure modes

| Risk | Why it matters | Required control/evidence before any adoption |
|---|---|---|
| Prompt injection from email/site/source | untrusted content can request data disclosure or actions | treat content as data; model cannot grant permissions; only narrow typed tools |
| Unexpected/duplicate send | browser timeout may happen after remote commit | durable effect ID, state UNKNOWN, original-site reconciliation, no blind retry |
| Stale approval | portal conversation or proposed change changes after review | digest of full intent + source version + expiry; re-fetch before effect; invalidate on mismatch |
| Framework replay/retry | checkpoint/workflow re-executes nodes or steps | isolate side effect; consult effect ledger; test every crash boundary |
| Leaked browser auth | storage files may impersonate the user | local protected file, never GitHub/logs/cloud model prompts; narrow profile; explicit retention |
| Background process leak | inference/browser/app can remain resident after task | capture process tree, bounded stop, exit confirmation, idle-residue measurement |
| OS/version mismatch | MXC gates depend on exact Windows UBR; current snapshot not enough | read exact Windows edition/build/UBR and capability before evaluating |
| License confusion | app license does not license model weights or provider use | inventory each package/model/service and intended personal/commercial use |
| Free-tier overage/region denial | hosted quotas/paid features or blocked country can invalidate plan | verify current official terms/account state before activation; unknown means deny |
| Stale knowledge index | local RAG may lag Notion and carry partial source text | treat it as derived cache with hash/version/tombstones and explicit readback |
| Battery/sleep/reboot | network effect may be in-flight while task stops | persist before work; transition effect to UNKNOWN after interruption; reconcile after restart |
| Excess architecture | agent framework, daemon, DB, vector store or cloud service may add cost without solving a real gap | compare against one-shot baseline and drop any component without measured benefit |

Security framing follows OWASP's current prompt-injection and excessive-agency risks: high-consequence action needs application-enforced human approval and minimized capability. A model instruction saying “ask me first” is not an authorization control.
