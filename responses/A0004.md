## 1. Decision brief

The smallest defensible starting point is an existing, narrowly constrained local capability, compared against deterministic retrieval without an LLM. There is no evidence yet that a fresh framework, cloud account, embedding database, additional resident model or custom service would improve this laptop's first useful job.

Carry at most three candidates into a later, separately authorized comparison:

1. **Existing Jan Agent + Jan Desktop local engine**, retaining the successful Jan-v3.5-4B read-file witness, but only after installed-version permission and resource gates. The witness is narrow; it does not certify the host's default permissions, general tool reliability or restart semantics.
2. **A demand-run deterministic Windows worker**, with Python's already observed standard library as the lowest-installation implementation candidate, optional existing localhost inference, and manual review. This is a proposed host, not existing working software and not a mandate to use Python.
3. **A Go native demand-run worker**, if candidate 2's packaging, lifecycle or measured process overhead creates a demonstrated gap worth adding a toolchain. Go is a serious alternative, not an approved installation or an assumed performance winner.

LM Studio Bionic is a substantive ready-app comparison, but **eligibility HOLD**: the current LM Studio App Terms contain a sanctioned-country location/residence representation. For this Iran-based user, do not classify local/free Bionic or LM Studio as cleared for future use without publisher clarification of applicable terms and eligibility. This is a contractual research finding, not a determination that all local AI software is illegal, and it authorizes no uninstall or device change.

Goose is a credible distinct ready-host fallback, but a new installation has not earned priority over the installed Jan witness. A hybrid free-cloud path remains **CONDITIONAL, NOT ACTIVATED**: this research did not establish an end-to-end renewable-free inference plus search route whose Iranian eligibility, account entitlement, data terms and hard spending stop are all verified.

The immediate next device action should be **one user-consented, read-only D0 observation**, defined in section 9. It starts no model or service. Then the coordinator can choose one bounded synthetic pilot. No production stack has won.

### 5.3 Ready-host security and practical differences

**Jan modes are separate controls.** Official [run modes](https://docs.jan.ai/agent/run-modes) distinguish plain default automatic tool approval, safe approval prompts, plan without write/execute, and OS sandboxing. Windows shell is unsandboxed unless the sandbox option applies. Approval is not confinement. CLI help from the installed nightly must be checked later; rolling documentation may describe newer behavior.

[Permissions](https://docs.jan.ai/agent/permissions) adds crucial caveats: safe mode does not prompt for dedicated memory/skill writes; explicit denies take precedence; home reads need restriction; network denial for sandboxed shell does not necessarily deny built-in web tools. Old “bash” rules do not necessarily deny the current “shell” tool. Therefore the synthetic pilot requires an explicit restrictive policy, not just a reassuring mode name. No escalation outside confinement, MCP, memory/skill modification or unknown network tool should be allowed. If installed controls cannot express that boundary, stop rather than rely on the model.

[CLI](https://docs.jan.ai/agent/cli) and [sessions](https://docs.jan.ai/agent/sessions) are relevant to later version-matched inspection and resume. Session transcripts can preserve conversational history; they do not prove exactly-once domain results. Do not run a plain default jan command as a diagnostic.

**Bionic** [project behavior](https://lmstudio.ai/docs/bionic/agent/work-project) distinguishes managed project copies from external files, which can be edited in place. [Quick start](https://lmstudio.ai/docs/bionic/quick-start) coding permission enables editing/shell features. A project UI is not proof that every external file is OS-isolated. Use only synthetic copies in any future eligible trial. [Overview](https://lmstudio.ai/docs/bionic), [models](https://lmstudio.ai/docs/bionic/models), [credits](https://lmstudio.ai/docs/bionic/accounts-plans-and-billing/credits-and-usage) and [pricing](https://lmstudio.ai/pricing) establish local/cloud separation; they do not establish this user's eligibility or quantitative free-search entitlement.

**Goose** [permission documentation](https://goose-docs.ai/docs/guides/managing-tools/goose-permissions/) states Auto default and model-based approval classifications; Smart Approve is best effort. Chat-only disables extension execution but cannot perform the desired tools. Do not use model classification as a security boundary. [Native installation](https://goose-docs.ai/docs/getting-started/installation/) does not require WSL. Source inspection of [desktop package.json](https://github.com/aaif-goose/goose/blob/main/ui/desktop/package.json), blob 7cf1cf900a103ea1821cf009a76b6606066f34e9, confirms Electron/Forge, version 1.55.0; Node ^24.10/pnpm are build dependencies. ### 6.4 Proposed resource policy, not measured limits

Start manual, one admitted job, one model, no background embedding/second agent/model warmup. Deterministic retrieval first; send only top relevant passages. Proposed initial model fixture: about 2K context if supported, expand toward the witnessed ~4K only if complete input/output budget and resource envelope permit; bounded output and at most one approved read-only tool invocation before reassessment. Do not truncate required citation evidence invisibly.

Admission uses current available RAM and commit headroom, not a fixed physical-memory percentage alone. A candidate must expose cancellation and a bounded queue; extra requests are rejected/queued with status, not used to start a second server. On OOM, repeated template error, unresponsive foreground, unknown tool, unexpected outbound host or failed cancellation: stop the attempt and record evidence; no automatic GPU/engine/provider escalation.

A later pilot can propose a conservative initial **1-GiB available-memory admission reserve** and a **0.75-GiB available or 85%-commit tripwire**, but these are unvalidated experiment parameters, not a proven safe operating envelope. If the baseline already violates them, remain deterministic/manual and review the plan. GPU driver failures and latency can occur above these thresholds; monitors may miss brief peaks. The coordinator/user must review thresholds before testing. A native process memory cap may cause controlled failure, not make an oversized model fit.

Measure baseline and cold start separately, then a few identical warm runs; record every sample, median/range and failures. Three runs cannot justify a stable p95. CPU cumulative seconds require interval deltas; report whole-machine normalization and logical CPU count. Record wall time/first token, actual input/output tokens, RSS/working set, private bytes, system commit/limit, available, page faults/disk activity, GPU dedicated/shared, idle-after-unload, battery/AC and observed responsiveness. Battery-life claims require longer controlled measurement, not one snapshot.

[Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects) can help custom-host process grouping, CPU/memory limits and owned-child cleanup, subject to nesting/breakaway behavior; they are not filesystem/network isolation or a GPU-VRAM cap. No settings or process limits are applied here. Native Resource Monitor/Task Manager/CIM suffice for observation before adding external managers. Do not use fake RAM optimizers, empty-working-set tricks or pagefile tuning as a model optimization.

Model unload must be demonstrated per engine: Ollama keep_alive, LM Studio JIT TTL/manual unload, Jan installed engine controls, standalone process exit or version-specific idle sleep. Closing a UI, ending a request, unloading weights and stopping a server are four different events. A scheduled worker should wait outside model residency and release the owned model only under an agreed engine ownership policy; never kill another user's/shared app process.

### 8.2 Canonical projection and state

Notion remains canonical. A selected local projection is explicitly dated, incomplete and read-only with respect to source originals. A manifest should record source page ID/URL, page title, source version or edited timestamp, acquisition time, selected heading/span, raw content hash, extraction tool/version, normalization version and completeness status. Store only the few pages needed for this task; no full private workspace export.

When a snapshot is stale, label it stale and request a refresh; do not claim it is current because it is local. A missing page in a partial export is **unknown**, not a tombstone. A deletion/tombstone requires authoritative evidence or a complete enumeration under a defined policy. Source conflict is surfaced with both versions, not silently overwritten. Hash changes without source-version changes are an extraction/provenance issue to investigate.

The trusted application should own:
- Fixed input root and exact file allowlist, canonical path validation and rejection of traversal/reparse-point/junction escape.
- Known operations such as READ_TEXT, LEXICAL_SEARCH, COMPARE_PUBLIC_VERSION and PROPOSE_RESULT; never free-form generated shell.
- Schema validation and source-reference validation outside the model.
- Explicit output-path and write approval; secrets never enter prompts or logs.
- Fixed network allowlist, time/byte/rate bounds and no unknown provider fallback.
- A durable job/result envelope. A model's statement “saved” is not a persistence check.

Proposed state machine: RECEIVED → VALIDATED → READ_COMPLETE → PROPOSAL_READY → AWAITING_WRITE_APPROVAL → RESULT_COMMITTED, with FAILED/CANCELLED/UNKNOWN terminal review states. Persist only where later approved. Separate job ID, attempt ID, input-manifest digest, action digest, result digest and receipt. Same job + same digest can return an existing committed result; same ID + different digest is a conflict, not a retry. A transcript alone does not resolve this.

A filesystem design needs atomic replacement/durable-write/recovery review; an SQLite transaction can atomically record internal result+receipt, but does not make an unrelated external operation exactly-once. Stage and reconcile ambiguous interruption; do not label success before readback. No pilot promise covers power loss, multiwriter operation or website SEND. This preserves A0003's P1-A/P1-B boundary.

Before reading documents, classify the Persian request and consult only selected capability records from the **original Applied v0.39 catalog**: permitted file read, lexical retrieval, citation validation, source comparison and durable result/recovery as applicable. Preserve each selected record's actual identifier, source page/version and evidence status in the later authorized projection; do not invent General IDs or assume the entire catalog belongs in the prompt. ### 9.1 D0: the next one smallest on-device step

Ask the user separately to run **one short local D0 snapshot** in the already available Windows PowerShell, with ordinary user permissions, while leaving their current app state unchanged. It observes current RAM/commit, Windows UBR, system-volume free space, selected assistant process metadata and selected listener ownership. It does not run inference, start apps/services, invoke Jan, install anything, read documents/config/credentials, alter settings, kill processes, create files or transmit output.

This is a proposed copy/paste block for later consent, not a request for approval in this report and not code executed by Work. Standard diagnostic reads may still create normal OS auditing activity; “read-only” here means no intentional configuration, content or application-state mutation. Review output locally before sharing; usernames/paths and unrelated names can be redacted. Do not paste full environment variables, command lines, API keys or raw application configuration.

~~~powershell
# PROPOSED D0 ONLY — NOT RUN BY WORK
# Ordinary Windows PowerShell 5.1; local reads, no model/API request.
$rbNow = (Get-Date).ToUniversalTime().ToString('o')
$rbOs = Get-CimInstance Win32_OperatingSystem
$rbMem = Get-CimInstance Win32_PerfFormattedData_PerfOS_Memory
$rbCv = Get-ItemProperty 'HKLM:\SOFTWARE\Microsoft\Windows NT\CurrentVersion'
$rbSysDisk = Get-CimInstance Win32_LogicalDisk -Filter "DeviceID='$($env:SystemDrive)'"
[pscustomobject]@{
  ObservedUTC = $rbNow
  WindowsEdition = $rbOs.Caption
  Build = $rbCv.CurrentBuildNumber
  UBR = $rbCv.UBR
  DisplayVersion = $rbCv.DisplayVersion
  VisibleGiB = [math]::Round($rbOs.TotalVisibleMemorySize / 1MB, 2)
  AvailableMiB = $rbMem.AvailableMBytes
  CommittedGiB = [math]::Round($rbMem.CommittedBytes / 1GB, 2)
  CommitLimitGiB = [math]::Round($rbMem.CommitLimit / 1GB, 2)
  CommitPct = $rbMem.PercentCommittedBytesInUse
  SystemDriveFreeGiB = [math]::Round($rbSysDisk.FreeSpace / 1GB, 2)
} | Format-List

# Selected names only; no command line, environment, open document or account data.
$rbAllProc = @(Get-CimInstance Win32_Process)
$rbSeeds = @($rbAllProc | Where-Object {
  $_.Name -match '^(jan|jan-agent|llama-server|llama-cli|ollama|lms|llmster|bionic|lm studio|goose|python|pythonw)\.exe$'
})
# Include descendants by PID relationship, even if helper names differ.
$rbIds = @($rbSeeds | ForEach-Object { [uint32]$_.ProcessId })
do {
  $rbExtra = @($rbAllProc | Where-Object {
    ($rbIds -contains [uint32]$_.ParentProcessId) -and
    ($rbIds -notcontains [uint32]$_.ProcessId)
  } | ForEach-Object { [uint32]$_.ProcessId })
  if ($rbExtra.Count -gt 0) { $rbIds += $rbExtra }
} while ($rbExtra.Count -gt 0)
$rbSelected = @($rbAllProc | Where-Object {
  $rbIds -contains [uint32]$_.ProcessId
})
$rbSelected | Select-Object Name,ProcessId,ParentProcessId,
  @{n='WorkingSetMiB';e={[math]::Round([double]$_.WorkingSetSize/1MB,1)}},
  @{n='PrivateBytesMiB';e={[math]::Round([double]$_.PrivatePageCount/1MB,1)}},
  @{n='CPUSecondsTotal';e={
    [math]::Round(([double]$_.KernelModeTime+[double]$_.UserModeTime)/1e7,2)
  }} | Format-Table -AutoSize

# Metadata only; known assistant ports or selected-process listeners.
if (Get-Command Get-NetTCPConnection -ErrorAction SilentlyContinue) {
  Get-NetTCPConnection -State Listen -ErrorAction SilentlyContinue |
    Where-Object {
      ($rbIds -contains [uint32]$_.OwningProcess) -or
      ($_.LocalPort -in @(1337,1234,11434))
    } | Select-Object LocalAddress,LocalPort,OwningProcess |
      Format-Table -AutoSize
}
~~~

Interpretation:
- No matching process means **not observed in this sample**, not “uninstalled.” Names can differ, and the seed filter may need a known executable name supplied by the user. Descendants may exit during the snapshot; PID reuse/races are possible.
- CPUSecondsTotal is cumulative CPU time, not instantaneous percent. Working-set totals can double-count shared pages. Commit is system-wide. A listener does not prove model readiness or API safety; 0.0.0.0/:: indicates a broader bind and is a reason to review before a pilot, not permission to change firewall/config.
- CIM unavailable/access denied is **unknown**, not zero. Do not rerun as administrator automatically.
- This block deliberately does not reproduce already established physical-RAM, Git/pip/FTS5 tests. It observes volatile facts plus missing UBR. It does not query local model APIs or infer current model presence from ports.
- D0 is sufficient for the next coordinator decision; the optional modules below are **not a request to run a large checklist**.
